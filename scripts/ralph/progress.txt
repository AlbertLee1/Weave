- PG functional expression index 命中规则：`CREATE INDEX ... ON tbl (((position->'coordinates'->>0)::float8))` 的索引 key 是**整个表达式**，WHERE 子句要逐字符匹配。`WHERE (position->'coordinates'->>0)::float8 BETWEEN ...` 走索引；写成 `position->'coordinates'->0` 或 `(position->'coordinates')->>0` 都不走。这意味着 Go 端拼 SQL 时不能"美化"表达式（去括号 / 改 cast 顺序），必须逐字符复刻 migration 里写的那一份。新加 functional 索引时把"WHERE 子句模板"作为注释钉在 .up.sql 顶部，避免日后调用方写歪。

- TimescaleDB continuous aggregate（cagg）"hit verification" 双手段：(1) `EXPLAIN <cagg SQL>` 文本要么命中 `<view_name>`，要么命中其底层 chunk 表 `_materialized_hypertable_*`——后者是 cagg 在 pg_class 里的实际表名，planner 在大多数版本会展开成它而非视图名。两者任一出现就算 hit；如果同时还出现裸 raw 表名（且不是 chunk 形式），那是 cagg 漏掉数据回查 raw，要重排查。(2) cagg 读完必须先 `CALL refresh_continuous_aggregate('<view>', NULL, NULL)`，否则 `WITH NO DATA` 子句会让 cagg 永远空表——所有 avg/sum/min/max/count 查询都返 0 行，first/last 因为走 raw 路径反而活着，是诊断 cagg 是否被正确读的最快线索。新加 cagg 集成测试模板：seed → refresh → query → EXPLAIN 双断言（cagg 名/chunk 名出现 + raw 表不在 cagg 外被引用）。参考 `pkg/timeseries/us467_pg_downsample_test.go` US-467。

- Continuous aggregate 物化 JSONB 数值列的标准套路：cagg 视图 SELECT 里 `AVG((value::text)::float8)` + `WHERE jsonb_typeof(value) = 'number'`，把非数值行从物化层过滤掉。校验放在 WHERE 而不是靠 cast 失败兜底——cagg 物化期一次 cast 失败会让整次 refresh fail，而 `jsonb_typeof` 是 immutable 函数，CAGG 限制允许在 WHERE 里出现。读路径上对应的 raw-table 查询也要 mirror 同一个过滤（pg_store.go 的 raw 分支也带 `jsonb_typeof(value)='number'`），否则 cagg 漏掉的 NULL avg 会被 raw 路径用"cast NaN"的不同语义错给客户端。参考 `migrations/000209_timeseries_cagg.up.sql` US-467。

- 多元组返回值扩字段时不要继续堆 tuple，统一用 outcome struct。`runCompensations` 原本 5-tuple `(compensations, edits, batchID, offset, dlqIDs)`，US-469 要加 FailedCompensations 第六个，与其再扩签名不如改成单一 `compensationOutcome` struct 返回，调用点写成 `compOut := ...; SagaResult{... - Saga compensation 的 stop-on-first vs best-effort 语义分界：best-effort 是"每个 compensator 都试"——broken prepare → DLQ + FailedCompensations + continue；commit-batch 失败 → 每个 build 出的 compensator 单独 DLQ + commit-phase FailedCompensations。stop-on-first 是"一旦失败就停"——第一个 prepare-failure 自身进 DLQ + FailedCompensations(phase=prepare)，后续未尝试的 prepared 步骤进 FailedCompensations(phase=skipped, DLQID=空) 但**不**入 DLQ（语义：未尝试 ≠ 失败，DLQ 是 retry 队列，没尝试过的不该被自动 retry）。两个 strategy 都要 echo `result.CompensationStrategy` 让 SDK 客户端确认服务端实际用的 mode；happy-path SUCCESS 也要 echo（不仅仅是 rollback 时）。FailedCompensationRef.ActionType **必须**从原始 reqs[i].ActionType 读，不要从 prepared.ActionType.APIName —— 后者已被 resolveActionType 标准化，客户端读到的应该是它原始传的那个 name（DTO 边界以输入为准，不要把内部规范化暴露给客户端）。参考 `pkg/actions/saga.go` US-469 的 runCompensations + primaryActionTypeName helper。

- Replay-style helper 的 "safe degrade" 设计：`ReplayDLQEntry` (lookup → publish → delete) 在 publish 失败时**保留** entry 让 operator 重试——理由：duplicate publish 由下游 idempotency dedupe 兜底（funnel 已经装好 sliding window），但 lost replay 没有任何兜底。delete 失败时反过来 swallow 进 log：publish 已 ack，多显示一行（直到下次 list refresh / poll tick）没有 functional 损失。这条决策有前置假设 "下游有 idempotency dedup"——任何抄这个 helper 但没装 idempotency 的场景必须显式校验。参考 `pkg/funnel/dlq_admin.go` US-470。

FOR UPDATE 锁 object_history 行（"version=N AND lock until commit"），属于后续 story 的范畴。当前实现的"快速失败"对绝大多数业务足够：caller 在多数情况下基于"已读到的 version"行动，而不是"刚才一瞬间的 version"。这条权衡写进测试注释，避免未来谁试图改成 true concurrent 又踩同一个坑。

- **Learnings for future iterations:**
  - **Quota 测试不能只断 `err != nil`，必须用时间上限把 abort 路径分开**。pkg/functions 三条 quota 互相之间会触发兜底：stack-overflow 兜底 timeout，timeout 兜底 OOM。如果只断 "err != nil"，写错 quota 的回归（如把 `MaxCallStackSize=8` 传成 `8000` 或 unwire MaxCallStackSize → vm 用默认 1024）依然能 pass 因为 timeout 1s 仍然 abort。修法：选一个**远低于** timeout 的预期 trip 上限（如 stack quota 必 <500ms 内 trip，timeout=1s），然后**反向**断 `!errors.Is(err, fnerrors.ErrTimeout)`。timeout 测试反过来 — 上下界双向钳制 `900ms ≤ elapsed ≤ 3s`，下界防 watchdog 提前 fire 误报（其他测试残留的 Interrupt 渗透），上界防 handler 5s 兜底接管。同款思路适用于：rate-limit / 重试预算 / pool 排队等任何"多层 fallback 都能 trigger error" 的场景。
  - **Config 加新字段必须显式 zero-value fallback，不能依赖 caller 用 DefaultConfig**。pkg/functions Config 是 PoD struct，Caller 普遍写 `Config{MaxA: 1, MaxB: 2}` 字面构造。新加 `MaxC int` 字段后 zero-init 成 0；如果 0 被 setter 视为 "无限制"（`vm.SetMaxCallStackSize(0)` 在 goja 里就是 unlimited），所有 pre-feature caller **静默解封**安全边界。修法：Execute 入口加 `if val <= 0 { val = defaultX }` 兜底，default 用包级常量。新加 quota 字段一并写两个 unit test：(a) explicit value 真正生效，(b) zero value fallback 到默认而不是解封。这条同样适用于 timeout / pool size / retry max 等任何"零值不等于无限制"的 quota 字段。
  - **多 PRD 字面 quota profile 并存的命名约定**：US-218 PRD = 5s/128MB，US-476 PRD = 1s/100MB/8。这两组数值都是 PRD 字面要求，谁覆盖谁都错。修法：不要改 `DefaultConfig()` 的字段值（会同时把上层一堆调用方推到不同 quota 区域），而是给每个 PRD-字面 profile 起独立 constructor 名字（`DefaultConfig`, `RestrictedConfig`, `RelaxedConfig`, `BatchConfig`...），doc comment 标注每个 profile 对应的 PRD story + 数值出处。Caller 显式选 `NewRuntime(RestrictedConfig())` 而非依赖 default。同款套路适用于：HTTP timeout / cache TTL / batch size / pool size / DLQ retention 等任何 PRD-numerical-driven config。
  - **handler-side ceiling 必须比 runtime-side ceiling 宽**才能在 BDD 里区分 "runtime quota 真的 fire" vs "handler 兜底接管"。pkg/oms.DefaultFunctionExecutionTimeout = 5s 是 ExecuteFunction handler 顶层 ceiling；pkg/functions.RestrictedConfig.MaxExecutionTime = 1s 是 runtime ceiling。BDD 测 timeout 路径时 `elapsed < 3s` 是关键 — 如果 runtime 没 wire 上 quota，handler 5s ceiling 会兜底，elapsed 会塌到 ~5s，BDD 立刻红。这条 elapsed-upper-bound 是验证"两层 ceiling 分别独立工作"的最便宜手段，比 mock handler / inject failpoint 都更稳。同款适用于任何"业务层 + handler 层双层超时"的设计（rate-limit / quota / lock acquisition 等）。
