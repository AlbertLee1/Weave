ForceAtlas2 needs every node to have a distinct seed position (it diverges when nodes share coordinates), so the adapter spreads inputs around a small radius-100 circle before calling the lib; on NaN/Infinity outputs it falls back to the seed position so downstream consumers always see finite x/y. Circular's upstream API exposes `scale` + `center` where `center` is a normalized 0..1 offset *multiplied* by `scale` to produce the translation — wrap it: run upstream with `center: 0.5` (offset = 0) and apply your own `radius` / `centerX` / `centerY` translation in the result loop for an unambiguous contract.
- **LayoutSpec as a kind-tagged union**: `type LayoutSpec = HierarchicalLayoutSpec | ForceLayoutSpec | CircularLayoutSpec | AutoLayoutSpec`. The LayoutApplier dispatches through a pure `computeLayoutPositions(spec, nodes, edges)` helper that resolves `auto` via `pickAutoLayoutKind(nodeCount)` first, then falls through to the concrete branch — keeps the React side a thin shell and makes the dispatch logic Vitest-friendly without touching Sigma. The Apply button's `data-testid` follows `vertex-layout-{kind}-apply` so the page test can drive each variant deterministically.
- **PATCH endpoints that mutate JSONB sub-fields**: prefer `jsonb_set(payload, '{key}', COALESCE(payload->'key', '{}'::jsonb) || $1::jsonb, true)` over a wholesale `jsonb_set` replacement. The `||` merges by key — single-entry PATCHes (e.g. drag of one node) don't clobber sibling keys, and the COALESCE seeds `{}` on first write so the operator has a left-hand side. Mirror the same merge semantics in MemRepo (parse → overwrite-by-key → re-marshal) so test fakes and PG diverge nowhere.
- **Pinned-aware layouts via post-overlay**: each layout helper (hierarchical / force / circular / future) accepts `pinnedPositions?: Map<id,LayoutPoint>` and calls a shared `applyPinnedOverrides(out, knownIds, pinned)` AFTER the algorithm runs. The algorithm sees the full graph (so unpinned siblings reflow around pinned anchors as if the pins were fixed); the post-step just overwrites layout-computed positions for pinned ids in the returned map. Unknown ids are silently ignored so callers can pass the entire pinned set without filtering.
- **Fetch→ready seed + user-diff state pair**: when state seeded from an async fetch must also be user-mutable, derive the seed via `useMemo` from the fetch response and store user mutations in a separate `useState<{set, cleared}>`. A second `useMemo` merges seed ⊕ diff into the effective view. Avoids the react-hooks/set-state-in-effect anti-pattern (which fires whenever the fetched payload changes) AND keeps user actions persistent across re-fetches. Pattern lands in VertexWorkspacePage.tsx for VTX-024 pinnedPositions but generalises to any "initial value from server, user can override" state.
- **Node-drag on Sigma**: subscribe `downNode` (capture node id + starting graph coords), `mousemovebody` (convert viewport coords via `sigma.viewportToGraph` → write to graph attrs + `sigma.refresh` + `event.preventDefault` to suppress camera pan), `mouseup` (read final coords + invoke onDragEnd callback). Use `mousemovebody` not `mousemove` so the drag continues when the cursor leaves the canvas. No need to disable the camera mouse captor — Sigma's pan handler triggers on `mousedown`-on-stage, not on `downNode`, so node drags don't compete with pans by default.
- **Multi-subscriber event handlers in mocked Sigma**: the existing `useRegisterEvents` mock uses `Object.assign` to merge handler sets, so two children registering the same event name (e.g. clickNode) silently overwrite each other. When adding a new Sigma child, audit existing children for event-name overlap; if necessary close popovers / state via document-level mousedown rather than Sigma's clickNode/clickStage. VertexNodeContextMenu hits this exact case — it listens only to `rightClickNode` and dismisses via a `document.addEventListener('mousedown', …)` in the menu-open useEffect.
- **graphology Graph vs MultiGraph**: the default `Graph` class rejects a second edge between the same source/target pair (throws on addEdgeWithKey, even with distinct keys). Use `import Graph, { MultiGraph } from 'graphology'` and `new MultiGraph()` whenever the payload can legitimately carry parallel edges (multiple LinkType instances between two objects, repeated relationships in time-windowed Vertex graphs, etc.). The single-edge `Graph` is fine for any consumer that pre-collapses or guarantees uniqueness.
- **Edge-merge reducer pattern (VTX-025)**: pure helper `mergeEdgesByLinkType(edges, {merge}) → VertexEdge[]` that buckets by (source, target, linkTypeRid) triple and attaches `count` + `label: ×N` + thicker `size` to multi-member groups. Singletons stay un-annotated so merge=on visually matches merge=off for already-unique edges; direction is preserved (A→B never merges with B→A — use a bidirectional LinkType class instead). Edges lacking `linkTypeRid` stream through ungrouped — we can't reason about "same kind" without it. The reducer runs INSIDE GraphLoader's effect so toggling the `mergeEnabled` prop re-builds the MultiGraph without churning the page-level projection.

- **Learnings for future iterations:**
  - Pattern: graphology's default `Graph` silently breaks any payload that carries multiple A→B edges — it throws on the second `addEdgeWithKey`. Switch to `MultiGraph` the moment a renderer needs to display parallel edges OR rely on a pre-merge pass that guarantees one-edge-per-pair. `import Graph, { MultiGraph } from 'graphology'` keeps the default `Graph` symbol available for any other consumer that needs the simple shape.
  - Pattern: an "edge reducer" in Vertex idiom is a pure `(edges, options) → edges` function. The reducer runs INSIDE the GraphLoader effect (not as a useMemo at the page level) so that toggling the option re-builds the graph by simply re-running the effect — no separate "rebuild" wiring needed, and the projection upstream stays stable.
  - Pattern: merge-style aggregation results should carry their count + label + size on the OUTPUT edge object, NOT on a separate side-channel map. Sigma's `getEdgeAttribute(key, 'label' | 'count' | 'size')` then has a single source of truth, and tests can assert on attributes without joining to an external lookup.
  - Pattern: toggle buttons in the Vertex TopBar use `aria-pressed={state}` + a conditional class block (blue-when-pressed) + a single onClick that flips the page-level state via `setX(v => !v)`. No popover needed for binary toggles.
  - Pattern: when extending an existing VertexEdge-style interface with optional fields (`count`, `label`, `size`, `linkTypeRid`), keep them `?:` so all existing call sites that build VertexEdge from scratch keep type-checking without explicit `undefined`. Producers (payloadToGraph, mergeEdgesByLinkType) only set the field when meaningfully non-empty; consumers check for `typeof === 'number'` / `typeof === 'string'` before reading.
