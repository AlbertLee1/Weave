- **Learnings for future iterations:**
  - cell key 用 *6 段* `${scenarioRid}::${objectType}::${primaryKey}::${property}::${atTimestamp}::${windowMs}`：VTX-040 是 3 段（rowRid 维度），VTX-041 是 4 段（对象属性维度），本 story 多两段 atTimestamp+windowMs 把"时窗"绑进 override 身份。React 接线层在 selectedTime 变化时不需要清旧 override —— key 不同自然不命中，旧 override 仍保留在 map 里等用户再回那个时刻还能看到。这与 spec "用户多次修改 selectedTime When 移动游标 Then override 仅对配置时窗生效" 直接对应。
  - agg 故意 **不** 进 key：override 表达"用户对该窗聚合代表值的认定"，与 view-side 当前展示的 agg 解耦。如果用户先用 avg view override 成 1500，然后切到 max view，1500 仍生效（"我说这个窗就该是 1500 不管你怎么聚合"）。若未来需求改成 "agg 切换要 invalidate override"，可加 agg 进 key —— 但目前 BDD spec 没要求，KISS。
  - smoothing 在两条路径生效：(1) 模型 input：computeTimeSeriesWindowAggregate 先桶化再 aggregateAtTime；(2) override 元数据：buildCreate body 含 smoothingMs 让后端记录"该 override 当时基于多大 smooth 窗口的展示值"。两者职责分开：smoothing 改了，未来读 override 仍然取 override.value（用户的认定）不重算；但若用户清掉 override，模型 input 回退到 smoothing 计算路径。
  - smoothSeriesByBucket 用 Map<bucketStart, {sum, count}> 累加而不是 group-by + reduce：对 N 个点是 O(N) 一次扫，比"先 sort 再 group"少一次 sort。前端通常时序点已经按时间升序（API 返回保证），但内部不 assume 让 API 调用方不必先 sort —— buildkey 用 floor 自然分桶，顺序无关。结果再按 t 升序保证下游 aggregateAtTime 行为可预测。
  - smoothSeriesByBucket 返回原序列 *副本*（`series.slice()`）而不是同引用，即使 bucketMs ≤ 0：纯函数原则 + 让调用方安全 mutate 返回值（如插入 selectedTime 处的 phantom 点用于绘制 cursor）不污染原始数据。同 VTX-041 applyObjectPropertyOverrides 的"返回带覆盖值的副本"原则一致。
  - computeTimeSeriesWindowAggregate 设计成"override 优先" 而非"smoothing 优先"：override 是用户的显式认定，应该 trump 任何自动计算。如果反过来 "smoothing 先 override 后"，那么 smoothing 配置变化会无意中"重算"override（用户已经说 1500 了，却被 smoothing 5min 算出 1000 覆盖），违反"override 仅对配置时窗生效"语义。
  - resolveTimeSeriesWindowCellEdit 锁 valueType='number'：时窗聚合 override 必然是 scalar 数值，不像 VTX-040/041 还要兼顾 string/boolean valueType。所以 invalid 路径只有 'not_a_number'，没有 'not_a_boolean'。React 接线层在渲染 Pane cell 时也不用让用户选 valueType —— 时窗 override cell 永远是 number input。
  - 服务端 endpoint 路径选 `/time-series-overrides` 而非复用 `/overrides`：与 VTX-040 parameter overrides + VTX-041 object-property-overrides 区分开。后端要起第三类表 scenario_time_series_overrides，列：scenario_rid, object_type, primary_key, property, at_timestamp BIGINT, window_ms BIGINT, agg TEXT, smoothing_ms BIGINT NULL, value DOUBLE PRECISION，唯一约束 (scenario_rid, object_type, primary_key, property, at_timestamp, window_ms)。三类 override 共用 scenario_runs/scenario_edits 历史链，但表分开让 schema 演化独立。
  - findTimeSeriesWindowOverride 取 WindowQuery 对象而不是 6 个位置参数：参数太多用位置形式容易调用方写错 atTimestamp/windowMs 顺序；对象命名让 IDE 自动补全 + 编译期 typo 检查。同 VTX-041 withScenarioId / applyObjectPropertyOverrides 风格一致（query/op 形式取对象，原子 helper 取位置）。
  - 测试 `given_OverrideAt5MinWindow_when_CursorMovesPast_then_OverlayNoLongerApplies` 是 spec BDD #3 "用户多次修改 selectedTime / override 仅对配置时窗生效" 的直接编码：先 set 一个 (AT, WIN_5MIN) override，apply 在同窗 → 1500；apply 在 AT+60s 窗 → null。这个测试是本 story 设计的核心证明 —— 如果 6 段 key 改成不含 atTimestamp，这个测试立刻红。
  - 后端 VTX-029 现有 stubOverlay 实现是 (scenario, object, property) → 单 scalar 替换所有 bucket（不分时窗），与本 story 的 (atTimestamp, windowMs) 维度 override 不齐。后端实现 story（VTX-002/VTX-043 路径）需要扩展 scenario overlay 让 query 时按时窗过滤匹配的 override；如果只命中"该 scenario 对该 (object, property) 有任意 override"就替换，违反"override 仅对配置时窗生效"。这里的差异要 backend story 注意。

- **Learnings for future iterations:**
  - VTX-043 同步 run 和 VTX-044 异步 run 共用 `/api/vertex/v1/scenarios/{rid}/run` 同一 endpoint：后端按 modelCount + body.forceAsync 决定 200 vs 202 响应。前端 `shouldRunAsync` 是**前端预判**（决定调哪个 builder + 是否在 POST 后立刻打开 SSE），不影响后端真实判定。两者必须对齐（modelCount 计算口径一致），否则前端预判 sync 但后端返回 202，会把 jobId 丢失；前端预判 async 但后端返回 200（少了 model），会等不到 SSE 事件。React 接线层在调 POST 前 `if (shouldRunAsync(...))` 立刻准备 EventSource 订阅，response.status === 202 时打开，否则按 VTX-043 走同步 parse。
  - `scenarioRunAsync.ts` 和 VTX-115 的 `web/src/vertex/scenarioRunStream.ts` 是**两套不同模块**，故意分开：(a) 事件 schema 不同 —— VTX-115 是 SDK 通用 RunEvent（progress/log/retry/completed/failed），VTX-044 是 Pane-aware ScenarioRunSseEvent（progress{model,pct}/result{model,output}/done/error{model?}/cancelled），后者带 model 维度让 Pane 表按 model 行渲染单独 progress bar；(b) URL 形状不同 —— VTX-115 用 `/run` + lastEventId query 走 resilient reconnect，VTX-044 用 `/run/{jobId}/stream` 走显式 jobId 路径（spec 直接要求）；(c) 职责不同 —— VTX-115 包 EventSource 实例 + 重连 + REST fallback，VTX-044 只管事件解析 + 状态机 + UI 派生，让 React 接线层自己选 EventSource 客户端（可以是 VTX-115 也可以是裸 EventSource）。两者将来可以组合：用 VTX-115 的 reconnect 客户端拉 `/run/{jobId}/stream`，每条事件喂给 VTX-044 的 parser/state machine。
  - SSE 事件解析的 `applyScenarioRunSseEvent(map, rid, event)` 对**未知 rid** 返回 map 同引用（不创建新 state）：spec §4.4 BDD 没明确"事件先于 POST response 到达怎么办"，但实践中（高延迟网络、Service Worker 缓存 SSE 响应、用户已切换 Pane）会触发该 race。如果在 unknown rid 上盲目创建 state，pending → progress 翻 running 会显示一个用户根本没点 Run 的 scenario 在跑，且没有 jobId 来 cancel。"同引用返回不重渲"是最安全的 default —— React 接线层在收到 SSE 事件前必须先 dispatch `applyAcceptedScenarioRunJob`（202 response 解析后），保证 state 已就位。本 story 测试 `given_no_state_for_rid_when_apply_event_then_noop_same_map_reference` 显式锁死该不变式。
  - `progressByModel: Record<string, number>` + `resultsByModel: Record<string, unknown>` 而不是 `Array<{ model, pct, output }>`：spec 没规定数据结构，但 React 渲 Pane Run 列时按 model row 查 `progressByModel[model]` 是 O(1)，而 Array 是 O(N)。N 通常 ≤10（Scenario 模型数量级），差异不大但 Record 形式让 setState merge 更自然（spread 单 key 替换 vs Array filter+push）。如果未来需要"按事件到达顺序回放"也可以从 SSE event log 重建，不必绑死内部数据结构。
  - `getOverallProgressPct(state)` 在 status='success' 时强制返回 100：spec §4.4 BDD #2 说"done{durationMs}" 是终态事件，但 done 不一定附带最后的 progress=100 事件（后端实现可以在 done 之前不发最后一条 progress=100）。如果不强制 100，UI 会显示"Running… 80%" 然后跳到 success ✓ 但 tooltip 仍说"80%"，反直觉。强制 100 让 success 的 progress bar 自然填满。同理 'cancelled' 不强制改 progress（cancelled 时 UI 显示用户被中断时的进度，让用户看到"我在 50% 时取消的"信息更友好）。
  - error 事件的 model 字段是**可选**而不是必需：spec §4.4 BDD #2 写"error{model,message}" 但 BDD #4 描述 workflow 超时取消是另一回事，workflow-level error（如总耗时超 limit）没有具体 model，前端需支持裸消息。parseScenarioRunSseEvent 对 `model` 字段做 `typeof === 'string' && trim().length > 0` 双重检查防 'M1' / '' / undefined 三态混淆，store error 时拼接 'M2: predict failed'（有 model）或裸 'workflow timeout'（无 model）。React 接线层在 tooltip 直接显示 error 字段，不再二次拼接。
  - `pending` 状态独立于 `running` 的原因：202 response 返回但 SSE 还没推任何事件时，UI 状态。如果合并成 running，spec BDD #3 "progress 才显示百分比" 的语义需要单独判断 `Object.keys(progressByModel).length === 0`，模块边界混乱。pending 状态让 tooltip 'Queued…' 文案与 running 'Running… N%' 区分开（pending 时进度未知，running 时至少有一个 model 有 pct），React Pane 接线层可以渲不同 spinner 颜色（Loader2 vs PauseCircle）让用户分清"已排队等开始" vs "正在跑"。但 icon 都返回 'spinner' —— Pane 列宽有限不区分细节。
  - Cancel 是双向交互：前端 POST cancel endpoint → 后端 ctx.Done → 当前 Activity cleanup → 后端推 SSE cancelled 事件 → 前端状态翻 cancelled。前端**不要**乐观更新（POST cancel 后立刻把 status 设为 cancelled），因为 cancel 可能失败（job 已完成 / 后端拒绝）。等 SSE cancelled 事件到达再翻状态，让 UI 与后端真实状态一致。POST cancel 的 response 仅作"请求已收到"信号（202），不携带最终状态。本 story 不暴露"乐观 cancel" helper，强制 React 接线层走 server-side cancellation。
  - `clampPct(value)` 在 parseSseEvent 里做而不是 applySseEvent 里做：解析层是 schema 边界，后端发 pct=200 是 contract 漂移，应在最早入口 normalize 防止下游 reduce 平均时把脏值放大（200 + 50 / 2 = 125 → tooltip 'Running… 125%' 反直觉）。同 VTX-040 parseScalarInput 把 'TRUE' 折成 'true' 也是在解析层 normalize。State machine 层假设输入已经 normalize 过，单一职责。
  - 测试 `given_pending_state_when_getTooltip_then_queued` 包含两步断言（pending 显示 'Queued…' → 收到第一条 progress 后切到 'Running…'），是因为 pending→running 的 transition 是 UX 关键 —— 用户点 Run 看到 'Queued…' 反馈，几百 ms 后看到 'Running… 0%' 进入活跃跑动，是 Palantir Foundry / Datadog Workflows 标准 UX。如果合并 pending=running，UI 会从 idle 直接跳到 'Running…' 没有"请求已收到"的过渡 confirmation，用户会怀疑是否点了按钮。
  - 模块复用 `ScenarioRef`（VTX-036）+ `immutableScenario` 工具（与 VTX-043 一致命名）：让 React 接线层在 sync vs async 路径共用 freeze 逻辑（`if (success) setScenarios(scenarios.map(s => s.rid===rid ? immutableScenario(s) : s))`），不必区分 VTX-043 / VTX-044 的 success handler。
  - 后端 endpoint 需要 backend story 实现 3 件套：(1) POST `/api/vertex/v1/scenarios/{rid}/run` body forceAsync 触发 202 + jobId + 启动 goroutine workflow（VTX-057 轻量 worker pool）；(2) GET `/run/{jobId}/stream` 走 chi route + `text/event-stream` 流（pkg/streaming 或新建 pkg/vertex/sse）+ 按 jobId 查 `scenario_runs` 表的事件历史 + 实时推 broadcast；(3) POST `/run/{jobId}/cancel` 触发 ctx.Done + 推 cancelled 事件 + cleanup workflow。本 story 仅锁定前端 API contract，后端实现细节走独立 story（VTX-057 + VTX-002 scenario_runs 表）。
  - dev-browser skill 不可用 — SSE 客户端打开 EventSource + 收到事件 + spinner+pct DOM 渲染 / Cancel 按钮点击 + cancelled toast 显示 / Pane Run 列绿 ✓ 红 × ⊘ 三色图标的浏览器验证留到 React 接线 story；本 story 仅交付纯逻辑层（5 类 SSE 事件解析 + 状态机 6 态迁移 + UI 派生 + 3 个 endpoint builder）。

- **Learnings for future iterations:**
  - ActiveScenarioState **不**塞进 ScenarioPaneState：scenarioPane.ts 是"Pane 表的结构"（列/行/CaseStudy/Scenarios），active 主视图是"用户当前 UI focus"（与表结构正交，可以横跨 Pane 与 SystemGraph 同时影响渲染）。如果耦合，scenarioPane reducer 必须每次 addScenario/removeScenario 处理 active 回退，模块边界混乱。本 story 选独立 state + clearActiveIfMissing 让 React 接线层显式两步走（removeScenario → clearActiveIfMissing），避免隐式联动。React 接线层把 ActiveScenarioState 作为 Zustand store 的独立 slice 即可。
  - BASELINE_COLUMN_KEY='baseline' 字面值故意与 scenario rid 形态错开：scenario rid 是 `ri.vertex.main.scenario.s-A` 格式（永远以 'ri.' 开头），'baseline' 不会撞 rid。setActiveColumnFromHeader 用 `columnKey === 'baseline'` 判断分支即可，不必把 BASELINE_COLUMN_KEY 跟随用户输入做转义。这与 React 路由的 `:type` 路径段习惯一致（baseline / explorer / quiver 都是已知 magic string）。
  - getMultiScenarioColumns 第一列总是 Baseline 而不是按 paneState.firstScenarioIsBaseline 开关：spec 没说"baseline 可隐藏"，且 BDD #1 显式要求"4 列并列：Baseline / S1 / S2 / S3"暗示 Baseline 是固定首列。如果未来 UX 改成"Baseline 可隐藏"，加 opts.includeBaseline=false 而不是改默认。Baseline 列的 isActive=true 表示"未选任何 scenario"，是 active state 的 null 标记的自然投影。
  - MultiScenarioReading.compare 用 BaselineCompareResult|null 而不是单独 deltaPct 字段：React 接线层渲染列时需要 simulated/baseline/delta/deltaPct/colorHint 五个字段一起（VTX-045 formatBaselineCompareLabel 接受整个 BaselineCompareResult），单字段返回会让调用方反向重组。Baseline 列自身 compare=null 不是 simulated===baseline 的 trivial compare（{delta:0,deltaPct:0,colorHint:'neutral'}）—— 后者会让 Baseline 列显示 "+0.0%" 标签，干扰视觉。null 明确表达"this column has no comparison target"。
  - buildReading 私有 helper + buildReadingsForKey 私有 helper：Pane row readings 和 Object readings 唯一差异是 outputs map 的 key 构造（buildPaneBaselineOutputKey vs buildObjectBaselineOutputKey），其它逻辑（遍历列、查 baseline、查 scenario、算 compare）共享。把共享部分抽进 buildReadingsForKey 让两个 public helper 只有 4 行身体（构造 key + 调 helper），避免维护两份相同 reading 算法。
  - getMultiScenarioColumns 缺 caseStudy 返回 [] 而不是只回 Baseline 列：spec BDD #1 把"Case Study 含 Baseline + 3 Scenarios"作为前提，无 Case Study 时 Pane 表头本身应该空（VTX-036 getColumnHeaders 已经这么做），与 paneState.caseStudy === null 的语义一致。React 层无 caseStudy 时根本不渲染 Pane 列头，本 helper 返回 [] 让 React 层直接 .map 出空数组而不必先判空。
  - getNodeColoringOutputs 用 `Object.freeze({})` 兜底而不是新建空对象：缺 scenario outputs 场景（用户切到尚未跑过的 scenario）每次都返回同一个 frozen 引用让 React useMemo 不会因为"每次都新 {}"而误认为变化触发重渲。Object.freeze 顺便防御调用方写入污染共享空对象。
  - getScenarioOutput 用 `key in outputs` 而不是 `outputs[key] !== undefined`：scenarioOutputs 允许显式 null 值（与 VTX-045 BaselineOutputValue 包含 null 一致），但不允许 undefined（合约）。`in` 操作符正确区分"key 不在 map"（→ null 兜底）和"key 在 map 但值是 null"（→ 保留 null）。后者是后端显式发送 "this output is intentionally null" 的合法语义，前端应保留信号而不是当成"缺失"。
  - clearActiveIfMissing 接 `presentScenarioRids[]` 而不是 ScenarioPaneState：本 helper 不关心 paneState 的其他字段（rows / inputOutputColumns / caseStudy），只需要 scenarios 的 rid 列表。接 string[] 让 React 接线层灵活：可以传 `paneState.scenarios.map(s => s.rid)` 也可以传"backend authoritative scenario list"。这与 VTX-045 shouldDispatchBaseline 接 options + status 而不是 BaselineRunState 全状态对象的设计选择一致——helper 接最小依赖避免膨胀。
  - 模块复用 VTX-045 computeBaselineCompare / BaselineCompareResult / BaselineCompareColor / BaselineOutputValue / buildPaneBaselineOutputKey / buildObjectBaselineOutputKey + VTX-036 ScenarioPaneState 不重复实现：compare 派生 + outputs 标量域 + key 构造都是 cross-cutting concern，本 story 在它们之上派生"按 scenario 排列的多列读数"，是分层而非平移。如果未来 BaselineOutputValue 扩展（如加 'series' 类型），computeBaselineCompare 改完，本模块自然继承（已通过 typeof 'number' && Number.isFinite 守卫，新类型不会误进入 compare 路径）。
  - Pane Baseline 列 readings 在 baseline=0 时 deltaPct=null 但 colorHint 仍非 null —— 不变式由 test `given_baseline_zero_when_get_then_scenario_deltaPct_null_but_colorHint_present` 在 Object readings 路径锁死。VTX-045 computeBaselineCompare 已经在 baseline=0 时返回 deltaPct=null + colorHint 仍按 delta 符号算（'positive' / 'negative' / 'neutral'），本模块直接透传。React 接线层 formatBaselineCompareLabel(result) 会按 deltaPct === null 回退到绝对带符号 delta（'+500'），与 VTX-062 baseline vs simulated 对比 Extended Label 的渲染逻辑天然兼容。
  - 本 story 设计了三个独立 helper（getColumns + getReadings + getColoring）而不是一个 mega helper "getEverythingForRender"：React 接线层在不同组件分别消费 —— Pane Table headerGroup 用 getColumns；Pane Table cell renderer 用 getMultiScenarioPaneRowReadings；SystemGraph 节点 Extended Label 用 getMultiScenarioObjectReadings；SystemGraph 节点着色器用 getNodeColoringSource/Outputs。组件粒度分开避免一个 hook 拉所有数据导致无关重渲。VTX-036 progress 也提到 "helper 不要膨胀为业务规则枢纽"。
  - VTX-062 (priority 62) "baseline vs simulated 对比 Extended Label" 是本 story 的下游消费者：将来 React 接线层调 getMultiScenarioObjectReadings 得到 N 列 reading[]，对每个 reading[i].kind === 'scenario' && reading[i].compare !== null 套 formatBaselineCompareLabel(reading[i].compare!) 渲染 "1500 (baseline 1000, +50%)" 字面值 + 按 colorHint 上色。本 story 把数据派生 + spec BDD #1/#2 多列读数交付，VTX-062 只负责把单条 reading 渲染成 React 节点（与 VTX-045 formatBaselineCompareLabel 拼接）。

  - **沙箱 + tempfile 的致命组合**：`install_filesystem_sandbox(denylist=[tmp_path])` 后，`with tempfile.TemporaryDirectory()` 的 `__exit__` 会触发 `shutil.rmtree` → 我们的 guarded `os.open` → `SandboxViolation` → rmtree 的 `onerror` 回调再次 rmtree → 无限递归直到 Python recursion limit。修复模式：测试用 `tmp_path` fixture（pytest 在 session 末做清理，与本测试解耦）+ 显式 `try/finally` 在测试体内调 `uninstall_filesystem_sandbox()`，**不要** 把 sandbox 套在 `TemporaryDirectory` 上下文内层。autouse fixture 的 `yield → uninstall` 顺序不够安全，因为 `with` 块的 `__exit__` 在 fixture cleanup 之前跑。

- **Learnings for future iterations:**
  - **隐式 DAG 优于显式 DAG**：BDD #1 给出的是 "M1 写属性 A，M2 读属性 A → M1 在 M2 前跑"，没有要求用户显式传 edges。这意味着规划器从 InputProperties / OutputProperties 自动派生 edges，用户提交的 ModelNode 只要声明 I/O 属性即可。这与 dataflow programming 的传统范式（Spark / Airflow）一致。如果以后要支持「按时序触发」「按事件触发」等非数据流依赖，加 ModelNode.ExplicitDeps `[]string` 字段不打破现有形。
  - **Kahn + DFS-fallback 两阶段 cycle 检测**：Kahn 算法用 in-degree 剥皮，O(V+E) 拓扑排序顺手；剥不出新层立刻知道有 cycle 但拿不到 cycle path。fallback 走一次 DFS（在残余 in-degree>0 子图上）追 grey-edge 还原 path。两阶段比"只用 DFS"更快（happy path 不会 DFS），比"只用 Kahn"信息更全（caller 拿到具体的 m1→m2→m1 而不是空指针）。这与 npm semver/cycle 检测的常用做法一致。
  - **自环（self-loop）= 1-model cycle**：M1 同时声明 InputProperties=[A] + OutputProperties=[A] 的 edge case 在 BuildDependencyGraph 里被允许（建出 m1→m1 边），由 TopologicalLayers 当 cycle 拒。这避免了在建图阶段先做"是否自环"特判 —— cycle 检测路径已经覆盖；测试 `Given_SelfLoop_When_Sort_Then_ErrCycleDetected` 锁死语义。
  - **CycleError 实现 `Is(target)` 让 sentinel + 富错并存**：调用方 `errors.Is(err, ErrCycleDetected)` 拿"是不是 cycle"，`errors.As(err, &ce *CycleError)` 拿 cycle 路径。两套接口共存的关键是给 CycleError.Is(target) 实现 `target == ErrCycleDetected`，否则 `errors.Is` 不会下钻到 *CycleError。这与 Go 标准库的 `os.PathError` 同模式。
  - **Runner concurrency 兜底语义**：`Concurrency <= 0` 自动设为 layer 宽度（"unbounded within layer"），`Concurrency > layerWidth` 也降为 layerWidth（避免起多余 goroutine）。这两个兜底让 zero-value `&Runner{}` 立刻可用，不需要 caller 算 GOMAXPROCS。production wiring 一般传 `Concurrency = N * runtime.GOMAXPROCS(0)` 之类的全局配置以保护 funcruntime sidecar。
  - **真·并发测试**：用 `atomic.AddInt32` + 共享 channel barrier 验证两个 sibling 真在 exec 内同时存在，而不是 "一前一后但很快"。第二个进入 exec 的 goroutine `close(siblingsInFlight)`，第一个 select 等待该 channel 关闭（带 2s timeout 兜底）。这比"测时长 < 50ms"之类经验阈值更可靠（CI/本机 jitter 可能让单线程跑也 < 50ms）。
  - **3-model chain benchmark < 3s 用 50ms sleep 模拟 exec**：BDD #4 的 "3 s" 是给真实 model 调用预算的（含 funcruntime HTTP RTT），单测里没有真 model 所以用 sleep 模拟典型 model 调用延迟。线性链路总延迟 = 3 × 50ms = 150ms，远低于 3s 阈值，实测 0.15s 通过。如果未来 funcruntime 平均 latency 突增，benchmark guard 也会触发（让 CI 暴露问题）。
  - **plan 与 run 端点拆分**：plan 是 dry-run（不调 executor），run 是 plan + 执行。Vertex Scenario UI 在用户提交"运行 mesh"按钮前可以先调 plan 显示 "M1 → M2 → M3 / M4" 给用户预览 + 暴露 cycle 错误，避免 round-trip 浪费。这与 SQL EXPLAIN vs EXECUTE / git plan vs apply 的分层一致。两个 endpoint 共享 meshRequest 形保持一致。
  - **executor 注入而不是注册**：Handler 在 NewHandler 时拿一个 ModelExecutor func（而不是 Register/Lookup interface）。意图：mesh runner 内部不区分 Function 是 Python sandbox / HTTP wrapper / function-backed action，统一抽象成 "given a model node, side-effect happens"，让 wiring 层（cmd/server/main.go）把 dispatch table（按 functionRID 路由到 funcruntime 或 modelfunctions wrapper）藏在闭包里。这避免 modelmesh 包反向依赖 funcruntime / modelfunctions 包。
  - **runLayer 即使中途 error 也排干 sibling**：测试 `Given_ModelFails_When_Run_Then_DownstreamSkipped` 锁死的语义是"下游 layer 不跑"而不是"同层 sibling 不跑"。原因：sibling 已经 dispatch goroutine 出去了，强行 ctx-cancel 会让 metric 不一致（部分 sibling 看见 ctx.Err 部分看见正常 result）。让 sibling 跑完再短路下游是更确定的失败模型，与 errgroup 的传统行为一致。如果未来需要 "fail-fast cancel sibling"，给 Runner 加 `FailFast bool` 而不是改默认。
  - **wiring 仍延后**：与前面 stream B 全部后端 story 同模式 —— `cmd/server/main.go` 注册 `modelmesh.Handler` 路由 + 注入真 ModelExecutor（按 functionRID 分发到 funcruntime client 或 modelfunctions wrapper，且写 scenario_edits 行）留给后续 wiring story。Handler 没有任何 PG 触达，无 migration。
  - **未来 wiring 时要考虑的 invoke 语义**：上游 model 写到 fork 的 property A，下游 model 读 property A —— 这意味着 ModelExecutor 在 Run 中写完 scenario_edits 后必须立即 flush 到 OSS 读路径上让下一层读到（要么 commit 后 read-through，要么 in-memory overlay）。这是本 story 范围之外的 Scenario 执行层职责；mesh 模块只保证 *layer 顺序*（M1 完成才开始 M2），不保证 *数据可见性*（那是 OSS Scenario reader 的责任）。
  - **dev-browser skill 不可用**：纯后端 story，无 UI 改动。BDD #1（拓扑序）/ #2（同层并发）/ #3（cycle 400）/ #4（benchmark）全部由 dag/runner/handler 测试覆盖，3-chain benchmark 实测 0.15s 远低于 3s 阈值。
