## Codebase Patterns
- ObjectSet executor Result can carry out-of-band per-PK payloads by adding a
  new map field (see Result.DerivedValues); handlers merge into WireObject
  Properties just before oss.FormatObject. Keeps Execute signature stable
  while avoiding a second backend roundtrip.
- withProperties Definition now takes DerivedProperties []DerivedPropertyDef;
  legacy Properties []string is still honoured and short-circuits to
  delegating to the inner ObjectSet unchanged.
- Link resolver mocks in objectset_test.go return a flat target list and
  ignore sourcePKs — for per-source tests add a new mock that maps each
  source PK to its own target list (see perPKLinkResolver in
  withproperties_test.go).
- withProperties numeric metrics (sum/avg/min/max) must resolve the target
  ObjectType via LinkTargetTypeResolver, then fetch per-PK docs from the
  target Bleve index with bleve.NewDocIDQuery + searchReq.Fields=[field].
  Test link resolvers need to implement ResolveTargetObjectType for these
  paths to work (plain ResolveLinkedObjectsByAPIName is NOT enough).
- bleve numeric field search results come back typed as float64 regardless
  of whether the source doc used int or float64 — coerceNumeric in
  executor.go handles the full int/uint/float spread to future-proof ingest
  paths that deviate.
- gofmt across the repo has pre-existing drift in many files; only lint your
  own edited files, do not blanket-reformat.
- Reverse-direction withProperties routes through an optional reverseLinkFinder
  interface (ResolveLinkedReverseByAPIName) on the link resolver; the executor
  short-circuits with an explicit error when a resolver only speaks forward.
  Test mocks must opt-in by adding the reverse method + reverseEdges map; the
  production *links.Resolver does NOT yet implement it, so end-to-end reverse
  withProperties still needs a follow-up adapter once OMS-backed incoming link
  lookups (ListIncomingLinkTypes) are wired through.
- Property now carries a Derived bool flag for US-004 (query-time computed
  fields). Three independent validators live alongside existing packages and
  can be wired into handlers incrementally without changing existing behaviour:
    * pkg/oms.ValidateObjectTypePrimaryKey (returns *apierror.APIError)
    * pkg/oss/where.ValidateClauseAgainstDerivedFields (sentinel error
      ErrDerivedPropertyTextSearchUnsupported; walks and/or/not subtrees)
    * pkg/actions.ValidateEditsAgainstDerived (sentinel error
      ErrDerivedPropertyReadOnly; delete edits always pass-through).
  Follow-up work: have handlers call these validators with a real derived-map
  fetched from OMS schema, so invalid requests surface on the wire.
- withProperties executor sorts its returned PrimaryKeys by
  (firstDerivedValue ASC, primaryKey ASC) as a deterministic composite sort
  key so offset-based LoadObjects pagination is stable across pages. The
  sort copies inner.PrimaryKeys before mutating so nested callers still see
  the inner executor's native order. compareDerivedValues tolerates nil,
  int64, float64 and string fallbacks so all five metrics plus future types
  remain orderable.
- interfaceBase execution in pkg/oss/objectset/executor.go now loads each
  implementing ObjectType concurrently (sync.WaitGroup + mutex-guarded map)
  and heap-merges their per-type buckets into a flat PrimaryKeys list. The
  per-type buckets survive on Result.PerTypePKs (sorted ASC) and per-row
  ObjectType on Result.Origins, so downstream consumers can drive
  composite-cursor pagination without re-sorting. The heap merge tie-break
  is (primaryKey ASC, objectType ASC) so PK collisions across types resolve
  deterministically.
- pkg/oss/pagination now has MultiTypeCursor{SubCursors []CompositeCursor}
  + Encode / DecodeMultiTypeCursor / IsExhausted. Use it as the wire format
  for any polymorphic paging scenario. Exhausted sub-cursors (inner == "")
  are dropped before Encode so the token shrinks as sub-streams drain.
- handler_preview.go has a dedicated writePreviewInterfacePage path that
  fires whenever result.PerTypePKs != nil. Rows are fetched from each
  row's own ObjectType Bleve index (not the interface-tag index), so
  $apiName / $rid / properties stay per-row accurate across a polymorphic
  result. The old offset cursor path is preserved as the fallback when
  PerTypePKs is nil.
- Integration tests under test/integration/ use //go:build integration.
  Boot a real PG via testutil.StartPGContainer + database.RunMigrationsUp,
  then construct oms.NewPGRepository(pg.Pool) as the metadata backend.
  Seed ObjectTypes via repo.CreateObjectType (primary_key_prop is just
  TEXT, so you can pass the string directly without creating Property
  rows). Bleve indexes stay in a t.TempDir() so there's no cross-test
  contamination. Production main.go does NOT yet wire a PG-backed
  InterfaceResolver, so tests that need one should ship a local shim:
  lookup via repo.GetInterfaceByAPIName(ctx, ontologyRID, apiName) →
  repo.ListInterfaceObjectTypes(ctx, iface.RID) → []apiName. Follow-up
  for Phase 6 Gate: fold that shim into main.go.
- New chi routes MUST update api/openapi.yaml AND re-copy to
  cmd/server/openapi_spec.yaml. `TestContract_AllRoutesDocumented` and
  `TestContract_EmbeddedSpecMatchesCanonical` both fail otherwise.
  Route in a protected group → remember to use `api.With(
  auth.RequirePermission(perm)).Method(http.MethodPost, path, handler)`
  so permission gating cascades through the existing auth middleware.
- For features that need a concrete-only PGRepository method (no
  cached-repo shim), main.go must keep a separate `pgRepo` handle at
  construction time (before wrapping in CachedRepository) and pass it
  through a typed ServerDeps field — unwrapping the cached decorator
  later is not supported.
- Narrow in-package interfaces beat expanding oms.Repository. The
  oms.Repository interface is already 50+ methods with 11 mock
  implementations; every new method forces 11 stub updates. If a
  consumer only needs 2–3 calls, define a local interface (see
  `pkg/index/rebuild.go RebuildRepo` and `rehydrate.go rehydrateRepo`)
  and keep the concrete PG method un-exported from the interface.
- Text FieldMapping defaults to the English ("en") Snowball analyzer
  via `pkg/index/mapping_builder.go:standardTextAnalyzer`. Lowercase
  + Porter stemmer + possessive strip is the baseline for
  analyzer.standard / unset properties; not_analyzed still routes to
  KeywordField (identity analyzer). When writing new text-field
  search tests prefer `bleve.NewMatchQuery(...)` — TermQuery skips
  the analyzer and breaks the moment a stemmer is in play. Use
  TermQuery ONLY on not_analyzed / keyword fields. Porter English
  does NOT stem "runner" → "run"; safe stem pairs for fixtures:
  run/runs/running, shoe/shoes, walk/walks/walking.
- oms.ObjectType returned by GetObjectTypeByAPIName does NOT carry
  its Properties slice — call ListProperties(ctx, ot.RID) separately
  and assign ot.Properties = props before handing the ObjectType to
  `index.BuildMapping`, otherwise the generated mapping will be
  empty and every search will silently return zero hits.

### Learnings for future iterations:
- The `TestContract_AllRoutesDocumented` + `TestContract_EmbeddedSpecMatchesCanonical`
  pair is a hard gate on ANY new route: register a chi path → must add an
  openapi.yaml path entry → must `cp api/openapi.yaml
  cmd/server/openapi_spec.yaml`. The second step is easy to forget and the
  test failure surfaces as "embedded spec drifted".
- `oms.Repository` has 50+ methods and 11 mock implementations in the
  codebase. For new functionality that only needs a 2–3 method slice
  (GetOntology/GetObjectTypeByAPIName/ListProperties here), define a
  narrow local interface in the consuming package the same way
  `pkg/index/rehydrate.go` does with `rehydrateRepo`. That keeps the
  mock surface from expanding and frees the Repository interface from
  single-caller methods.
- The cached OMS repo decorator (`oms.NewCachedRepository`) wraps
  *PGRepository and hides any PG-only methods. If a feature needs a
  concrete PG-only method (here: `LoadLatestObjectStates`), main.go must
  stash the raw `*oms.PGRepository` handle at construction time and
  pass it through a separate typed dep — don't try to unwrap the
  cached repo later.
- PostgreSQL `SELECT DISTINCT ON (col1) ... ORDER BY col1, col2 DESC`
  is the idiomatic way to collapse a history table to the newest row per
  key. Remember the ORDER BY must start with the same column as DISTINCT
  ON or Postgres rejects the query.
- HTTP handler "not configured" (503) vs. "permission denied" (403) is a
  semantic distinction that matters for operators. A degraded-mode
  server with no PG pool should return 503 from admin endpoints, NOT
  401/403 — the caller is authorised, the feature is just disabled.
- The existing cmd/server package test harness uses stub types via the
  contract tests `contractOmsRepo{oms.Repository}` pattern (embedding +
  panic-on-use). For unit-testing specific handlers, prefer small
  hand-written stubs satisfying the narrow interface — embedding drags
  in the full 50-method surface and makes test failures harder to read.

- **Learnings for future iterations:**
  - bleve's implicit "standard" analyzer lowercases + tokenises but does
    NOT stem. If a future US wants Foundry-like root-form matching on a
    text field, the mapping builder must explicitly set
    FieldMapping.Analyzer = "en" (or another snowball language). Just
    leaving Analyzer blank keeps the old non-stemming behaviour.
  - Porter/Snowball English does NOT fold "runner" -> "run". It's a
    noun stem, not a verb form. Test fixtures that want a single query
    to hit multiple docs via stemming should prefer verb conjugations
    ("run"/"runs"/"running") — those all collapse to "run". Plural
    nouns (shoes -> shoe) and -ing/-s verbs are the safe bets.
  - TermQuery bypasses the field analyzer entirely — the raw surface
    form is matched against the indexed token. Any analyzer upgrade
    (lowercasing, stemming, stopword filters) can and will break
    previously passing TermQuery-based tests. Rule of thumb: use
    MatchQuery for text fields, reserve TermQuery for keyword
    (not_analyzed) fields where the analyzer is identity.
  - Property.TypeConfig round-trips through PG as JSONB: write with
    `json.RawMessage(...)`, read back with ListProperties, then use
    index.AnalyzerFromTypeConfig to extract the hint. The rehydrate
    bootstrap already does this dance — integration tests must too.
  - ObjectType.Properties is NOT populated by GetObjectTypeByAPIName;
    it's a separate ListProperties call keyed by the ObjectType RID.
    Manual hydration is required before BuildMapping can inspect the
    properties slice.
