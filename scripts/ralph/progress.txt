## Codebase Patterns
- Browser dogfood is mandatory for Vertex/Sigma runtime changes: Vitest/jsdom and `make web-test` can pass while the real Vite dev server throws React/Sigma runtime errors.
- Heavy ESM-prebundled libs that import `react` (e.g. `@react-sigma/core`) MUST live in `vite.config.ts` `optimizeDeps.include` when behind a `React.lazy` boundary. Pair with `resolve.dedupe: ['react', 'react-dom']`.
- Vitest tests that need to validate `vite.config.ts` content can use Vite's `?raw` query (`import src from '../../vite.config.ts?raw'`) — avoids `node:fs` imports that aren't typed in `tsconfig.app.json`.
- `internal/testutil.StartPGContainer(t)` is the project's canonical way to get a real PostgreSQL for integration tests; gate the test file with `//go:build integration`.
- Migrations live in `migrations/` numbered 000NNN with paired up/down SQL files; the next free number as of this iteration is 000205.
- `cmd/server/main.go` boots dependencies in a long deps struct (Config → PG → IndexManager → LinkResolver → OSSService → ObjectSetStore → NATS Consumer → ActionExecutor → router); GeotemporalStore is currently hard-wired to `geotemporal.NewMemoryStore()` at line ~2376.
- `pkg/mcp.Server` already has an `oms.Repository` injected; `prompts/list` / `prompts/get` can be added without changing the `NewServer` signature.

## Iteration intent
This iteration is the post-VTX-126 follow-on. Vertex v1 + browser fix shipped; we now resume the OSv2 deepening track from docs/PRD-Weave-OSv2-深度复刻-V2.md but **only** picking gaps still observable in code (not parroting items already shipped). The three picked stories:

- **OSV2-301 — GeoTemporal PG persistence** — `pkg/geotemporal/store.go` package doc explicitly says PostGIS/JSONB backend is "intentionally deferred"; `cmd/server/main.go` hard-codes `MemoryStore`. Result: `/api/v2/.../geotemporalSeries/.../latestValue` loses all points on process restart — a real correctness bug on the single-machine deployment Weave is meant to be. Owner of fix: add `pg_store.go` + migration 000205, wire as default when PG pool is non-nil.

- **OSV2-302 — MCP prompts/list real** — `pkg/mcp/server.go:107-108` hard-codes `prompts: []`; `pkg/mcp/doc.go:16` says "Weave does not yet expose prompts". Real MCP clients (Claude Desktop, Cursor) therefore cannot surface Weave ActionTypes as prompts. Fix: synthesize prompts from OMS ActionType metadata, implement `prompts/get`, advertise the `prompts` capability in `initialize`.

- **OSV2-303 — weave-mcp stdio truly usable** — `cmd/weave-mcp/main.go:5` literally calls itself a STUB and points users at the HTTP transport. To honour the doc comment's "supported MVP path" intent without bootstrapping PG/NATS twice, this story turns weave-mcp into a stdio↔HTTP bridge to `cmd/server` `POST /mcp`, so local AI clients can spawn `weave-mcp` and consume the same tools/resources/prompts (including the OSV2-302 prompts) as the HTTP transport does.

## 2026-05-16 08:15 — OSV2-302 — MCP prompts/list bound to OMS ActionType
- **Red:** wrote `pkg/mcp/prompts_test.go` with five BDD cases (one prompt per ActionType, arguments in declaration order with required flags, prompts/get renders user message, nil-OMS still returns empty list, initialize advertises prompts capability). Compile failed because `Prompt` / `PromptArgument` / `PromptMessage` types did not exist — that was the intended Red. Also discovered Response.Result is `any`, so tests use a `remarshal` helper to round-trip through JSON before strict decode.
- **Green:** new `pkg/mcp/prompts.go` with three exported types (Prompt/PromptArgument/PromptMessage) and the handler pair `handlePromptsList` + `handlePromptsGet`. Prompt names are `<ontologyApiName>__<actionApiName>` (double underscore to avoid colliding with single underscores already common in action api names). Arguments come from `ActionType.Parameters` (json.RawMessage of `[{id,type,required,description}]`), preserving declaration order. `prompts/get` resolves ontology apiName → RID via `GetOntology` first so both the PG repo (which already accepts either form) and the in-memory test fake (RID-keyed only) land on the same row. Rendered user message text always contains the ontology, action and supplied parameter k/v pairs in sorted order so tests are deterministic.
- **Capability advertisement:** `handleInitialize` now emits `capabilities.prompts: {listChanged: false}` alongside `tools` and `resources`. The existing `TestServer_PromptsList_EmptyOK` test still passes — when no ActionTypes are registered the list is naturally empty.
- **Files changed:**

  - `pkg/mcp/prompts_test.go` (new)
  - `pkg/mcp/server.go` (prompts/list + prompts/get dispatch, initialize capability)

  - `go vet ./...` — clean.

- **Learnings for future iterations:**
  - MCP `Response.Result` is `any` in this codebase, not `json.RawMessage` — tests that need strict decoding should remarshal via `json.Marshal` then `json.Unmarshal` (helper `remarshal(v, into)`).

## 2026-05-16 08:40 — OSV2-303 — weave-mcp stdio↔HTTP bridge
- **Red:** wrote `cmd/weave-mcp/main_test.go` with four BDD cases (initialize round-trip with prompts capability, tools/list verbatim forwarding, prompts/list verbatim forwarding, upstream-unreachable produces a JSON-RPC error line with the original id echoed). Compile failed because `RunHTTPBridge` did not exist — Red.
- **Green:** new `cmd/weave-mcp/http_bridge.go` with `RunHTTPBridge(ctx, in, out, url)` — a tiny stdio↔HTTP proxy that POSTs every newline-delimited JSON-RPC envelope to cmd/server's `POST /mcp` and writes the verbatim response back as a single line. Sniffs the id off the request so error lines on upstream failure still echo the right correlator. Notifications (no `id`) are forwarded but never produce an output line. The bridge intentionally returns `nil` on upstream errors and surfaces them as JSON-RPC error responses instead of crashing the binary — local MCP clients then see a transport-layer error code (`-32000`) per request rather than the subprocess dying mid-conversation.
- **Wiring:** `cmd/weave-mcp/main.go` rewritten — `WEAVE_MCP_URL` set ⇒ bridge mode; unset ⇒ legacy in-memory demo mode (preserved so framing-only tests can still run without a cmd/server). The "STUB" header notice in the file's doc comment is gone and replaced with the real two-mode contract plus a sample Claude Desktop `claude_desktop_config.json` snippet pointing at `http://127.0.0.1:9117/mcp`.
- **Files changed:**
  - `cmd/weave-mcp/http_bridge.go` (new)
  - `cmd/weave-mcp/main_test.go` (new)
  - `cmd/weave-mcp/main.go` (mode-switch + doc rewrite)
- **Quality gates (all green):**
  - `go test ./cmd/weave-mcp/... -count=1` — 4 new + 1 existing tests pass.
  - `go vet ./...` — clean.
  - `make test` — full Go suite green.
- **Operational note for follow-up:** the bridge does not currently inject Authorization headers. When cmd/server is run with `AUTH_MODE=token`, the operator must set `WEAVE_MCP_URL` to a URL form that includes auth (the project's `POST /mcp` already supports bearer tokens through chi middleware; wiring an env-passthrough is a single small addition if anyone hits it). For dev/local Claude Desktop the default `AUTH_MODE=dev` server needs nothing.
- **Learnings for future iterations:**
  - When a binary's doc comment self-identifies as "STUB", treat it as a real product gap on par with a TODO — the assertion shows up in `grep`s during planning and is the single best signal that something user-visible isn't yet wired.
  - Stdio MCP bridges should always emit one JSON-RPC line per request even on failure; a silent subprocess is the worst failure mode for Claude Desktop / Cursor because the client retries forever.
  - `http.Client{Timeout: 30s}` is appropriate for MCP — tool calls can be slow (semantic_search hits pgvector) but not multi-minute slow.
