- PG functional expression index 命中规则：`CREATE INDEX ... ON tbl (((position->'coordinates'->>0)::float8))` 的索引 key 是**整个表达式**，WHERE 子句要逐字符匹配。`WHERE (position->'coordinates'->>0)::float8 BETWEEN ...` 走索引；写成 `position->'coordinates'->0` 或 `(position->'coordinates')->>0` 都不走。这意味着 Go 端拼 SQL 时不能"美化"表达式（去括号 / 改 cast 顺序），必须逐字符复刻 migration 里写的那一份。新加 functional 索引时把"WHERE 子句模板"作为注释钉在 .up.sql 顶部，避免日后调用方写歪。

- TimescaleDB continuous aggregate（cagg）"hit verification" 双手段：(1) `EXPLAIN <cagg SQL>` 文本要么命中 `<view_name>`，要么命中其底层 chunk 表 `_materialized_hypertable_*`——后者是 cagg 在 pg_class 里的实际表名，planner 在大多数版本会展开成它而非视图名。两者任一出现就算 hit；如果同时还出现裸 raw 表名（且不是 chunk 形式），那是 cagg 漏掉数据回查 raw，要重排查。(2) cagg 读完必须先 `CALL refresh_continuous_aggregate('<view>', NULL, NULL)`，否则 `WITH NO DATA` 子句会让 cagg 永远空表——所有 avg/sum/min/max/count 查询都返 0 行，first/last 因为走 raw 路径反而活着，是诊断 cagg 是否被正确读的最快线索。新加 cagg 集成测试模板：seed → refresh → query → EXPLAIN 双断言（cagg 名/chunk 名出现 + raw 表不在 cagg 外被引用）。参考 `pkg/timeseries/us467_pg_downsample_test.go` US-467。
- "可选 capability + 三态原子缓存" 模式：当 store 的 cagg / 索引 / 扩展可能存在也可能不存在时，用 `atomic.Int32` 三态缓存（-1=unknown, 0=absent, 1=present），构造时 Store(-1)、`DetectXxx(ctx)` 探测后落盘，运行期分发逻辑只读 atomic 而不查 `pg_*` 元表（每查询查一次会拖性能）。lazy 探测保留为兜底——`if state.Load() == -1 { DetectXxx(ctx) }`，cmd/server 启动期主动调用 `DetectXxx` 让首请求不付探测代价。探测出 err / 表不存在统一 `state.Store(0) + return false`（degraded 模式静默 no-op），不要 panic / 不要 propagate err 给业务路径。参考 `pkg/timeseries.PGStore.DetectCAGG` + `useCAGG` + 三态 `caggKnown`（US-467）。
- Continuous aggregate 物化 JSONB 数值列的标准套路：cagg 视图 SELECT 里 `AVG((value::text)::float8)` + `WHERE jsonb_typeof(value) = 'number'`，把非数值行从物化层过滤掉。校验放在 WHERE 而不是靠 cast 失败兜底——cagg 物化期一次 cast 失败会让整次 refresh fail，而 `jsonb_typeof` 是 immutable 函数，CAGG 限制允许在 WHERE 里出现。读路径上对应的 raw-table 查询也要 mirror 同一个过滤（pg_store.go 的 raw 分支也带 `jsonb_typeof(value)='number'`），否则 cagg 漏掉的 NULL avg 会被 raw 路径用"cast NaN"的不同语义错给客户端。参考 `migrations/000209_timeseries_cagg.up.sql` US-467。
- pg_cron schedule + 应用层 ticker 二选一冗余的标准写法：migration 用 `IF EXISTS (SELECT 1 FROM pg_available_extensions WHERE name = 'pg_cron')` 包 `cron.schedule(name, '*/5 * * * *', $cmd$ CALL ... $cmd$)`；cmd/server boot 永远起一个 `RunCAGGRefreshLoop(ctx, store, 5*time.Minute, ...)` 协程，调用同一个 `refresh_continuous_aggregate` 入口（TimescaleDB 内部 serialize 重叠 refresh，幂等）。任一边出问题另一边兜住；degraded 模式（无 timescale 时 RefreshCAGG return nil）协程天然 no-op。新加自动维护任务（vacuum / reindex / cagg refresh / 数据归档）都走这套双轨。
- 多元组返回值扩字段时不要继续堆 tuple，统一用 outcome struct。`runCompensations` 原本 5-tuple `(compensations, edits, batchID, offset, dlqIDs)`，US-469 要加 FailedCompensations 第六个，与其再扩签名不如改成单一 `compensationOutcome` struct 返回，调用点写成 `compOut := ...; SagaResult{... Compensations: compOut.compensations, FailedCompensations: compOut.failedCompensations, ...}`。同一个 struct 同时承担了"happy-path 返回数据"和"error-path 返回 partial 数据"两种角色，避免每次扩字段都跨 5 个 callsite 改 5 处 tuple 拆解。任何 saga / batch / pipeline 协程的 inner helper 一旦返回 ≥4 个相关字段，都建议先用 outcome struct，再次扩字段时零搬运成本。参考 `pkg/actions/saga.go` US-469 段。
- Saga compensation 的 stop-on-first vs best-effort 语义分界：best-effort 是"每个 compensator 都试"——broken prepare → DLQ + FailedCompensations + continue；commit-batch 失败 → 每个 build 出的 compensator 单独 DLQ + commit-phase FailedCompensations。stop-on-first 是"一旦失败就停"——第一个 prepare-failure 自身进 DLQ + FailedCompensations(phase=prepare)，后续未尝试的 prepared 步骤进 FailedCompensations(phase=skipped, DLQID=空) 但**不**入 DLQ（语义：未尝试 ≠ 失败，DLQ 是 retry 队列，没尝试过的不该被自动 retry）。两个 strategy 都要 echo `result.CompensationStrategy` 让 SDK 客户端确认服务端实际用的 mode；happy-path SUCCESS 也要 echo（不仅仅是 rollback 时）。FailedCompensationRef.ActionType **必须**从原始 reqs[i].ActionType 读，不要从 prepared.ActionType.APIName —— 后者已被 resolveActionType 标准化，客户端读到的应该是它原始传的那个 name（DTO 边界以输入为准，不要把内部规范化暴露给客户端）。参考 `pkg/actions/saga.go` US-469 的 runCompensations + primaryActionTypeName helper。

  - cagg 物化 JSONB 数值列的"两边过滤"原则：cagg DDL 里 `WHERE jsonb_typeof(value)='number'` 把非数值行从物化层踢掉；raw 路径 SQL 也必须**同样的 WHERE**，否则两条路径返回不同行数（cagg 不算 NULL avg，raw 算 NaN）。这条"过滤要 mirror"是 cagg + raw 双路径系统的硬规则——加新过滤 / 改 cast 时要走 grep-diff cagg DDL ↔ pg_store.go 确认两边一致。已写进 Codebase Patterns。
  - pg_cron schedule + 应用层 ticker 双轨冗余：migration 用 `IF EXISTS pg_available_extensions WHERE name='pg_cron'` 包 `cron.schedule`，cmd/server 永远起 `RunCAGGRefreshLoop` 协程；TimescaleDB 内部 serialise 重叠 refresh 所以幂等。任一边出问题另一边兜住。新加任何"自动维护任务"（vacuum / reindex / cagg refresh / 数据归档）都按这套写法，不要因为 prod 有 pg_cron 就不写 app-side ticker——开发机 / 集成测试机基本都没 pg_cron。已写进 Codebase Patterns。
