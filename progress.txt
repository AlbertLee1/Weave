## Codebase Patterns
- ObjectSet snapshot subsystem has TWO distinct surfaces: (1) the in-memory `pkg/oss/objectset.Store` keyed by `createTemporary` RIDs (1h TTL), and (2) the durable `object_set_snapshots` table written via the `PersistedSnapshotStore` interface (US-224). The PG row interface lives in `pkg/oms` (`ObjectSetSnapshot` + `ObjectSetSnapshotStore`); the direction-of-dependency rule keeps `pkg/oms` from importing `pkg/oss/objectset`, so `cmd/server/object_set_snapshot_adapter.go` bridges them.
- A third durable surface — `saved_object_sets` (migration 000013) — is fully implemented (`pkg/oss/objectset/PGSavedStore`) but NOT YET wired into `cmd/server`. It has unit + integration tests but no HTTP route. New work that needs durable saved definitions can wire the existing store; no new schema is needed.
- Migration numbering convention: zero-padded `000NNN_description.{up,down}.sql`. Migrations are run with `golang-migrate`. As of US-365 the tip is migration 000082.
- Test build tags: unit tests run by default; `//go:build integration` tests need `go test -tags integration` and use `internal/testutil.StartPGContainer(t)` to boot a real Postgres container. The `ListEntries` helper on the in-memory `Store` is the canonical way to introspect ephemeral entries from tests.
- For canonical-JSON hashing across the codebase, prefer the `objectset.HashDefinition` helper (sorts keys, sha256 hex). Calling `json.Marshal` first is fine — the helper canonicalises again.
- Executor errors that need a non-default APIError mapping should be sentinels in `pkg/oss/objectset/executor.go` (e.g. `ErrQueryTooLarge`) and translated by the `executeError(err) *apierror.APIError` helper in `pkg/oss/objectset/handler.go`. All `h.executor.Execute` callers in this package go through that helper instead of hand-rolling `apierror.NewInvalidParameter("ObjectSetFailed", …)`. Add an `apierror.New<Code>` constructor in `pkg/apierror/error.go` for the wire-format code (e.g. `WEAVE_QUERY_TOO_LARGE` → 422).
- `pkg/oss/objectset/searcharound_path_test.go::seedMultiHopIndex` accepts `testing.TB` so unit tests AND benchmarks can share it. `multiHopResolver` is the canonical in-memory `LinkResolver` for path-traversal tests — it implements `ResolveLinkedObjectsByAPIName` (forward), `ResolveLinkedReverseByAPIName` (reverse), `ResolveTargetObjectType` and `ResolveTargetObjectTypeDir`. Bench paths should root at `Type:"static"` rather than `Type:"base"` to bypass Bleve in measurement loops; `Type:"base"` with the 10K cap can hang the in-memory Bleve index.
- `aggregation.AggregationRequest.Accuracy` is the Palantir-style request-level toggle (`ALLOW_APPROXIMATE` default, `REQUIRE_ACCURATE` opt-in). `computeMetrics(idx, baseQuery, specs, accuracyMode)` is the chokepoint that routes `approximateDistinct` → exact and `approximatePercentile` → sort-based exact when `REQUIRE_ACCURATE` is set. The fourth return value (`approximate bool`) flags when an approximate algorithm actually fired so the response.accuracy column reflects runtime truth, not just user intent. When adding a new approximate aggregation, route both the exact-fallback path AND the approximate-flag bookkeeping through this helper rather than emitting accuracy from the call site.
- HLL sparse-exact threshold: `1<<(precision-2)` (4096 at default p=14). Below this cardinality the axiomhq sketch is in its sparse compressed-list mode and returns byte-exact counts; above it transitions to dense estimation. Use `sparseExactThreshold(precision)` from `bleve_agg.go` rather than hard-coding the boundary, so a future precision change keeps the response.accuracy verdict consistent.
- `approximatePercentile` runs through `pkg/oss/aggregation/tdigest_percentile.go` (influxdata/tdigest) at compression `DefaultTDigestCompression=100`. That cap is the steady-state memory contract: max processed centroids `2c` + max unprocessed `8c` ≈ 16000 bytes ≤ 16 KiB ceiling (tested at 1M points). When a bucket has unit-weight centroids (any size below the digest's processed cap), Quantile reduces to *linear interpolation between two flanking sorted values at half-integer cumulative weights* — disagrees with HdrHistogram's nearest-rank/3-sig-fig convention, so any percentile reference test must use the same interpolation formula (see `phase6_percentile_groupby_test.go::referencePercentileForBucket`). HdrHistogram is no longer in the dependency graph.
- The `cmd/server` openapi contract test has TWO surfaces: every chi route must appear in `api/openapi.yaml`, AND `cmd/server/openapi_spec.yaml` must be byte-identical to `api/openapi.yaml`. New routes need both an entry in `api/openapi.yaml` and a `cp api/openapi.yaml cmd/server/openapi_spec.yaml` step before the contract suite goes green. The two failing tests are `TestContract_AllRoutesDocumented` and `TestContract_EmbeddedSpecMatchesCanonical`.

Idempotency conflicts surface as a sentinel error (`ErrSagaIdempotencyConflict`) detected via `errors.Is`; the executor races cleanly by re-reading the prior result row on the conflict branch.

- AIP Logic flow editor patterns: realtime client-side validation lives in `web/src/components/aiplogic/LogicFlowsPage.tsx::validateGraph(rfNodes, rfEdges)` returning a `ValidationReport` with `cycle` / `unconnected` / `unboundParam` issue kinds — keep this focused on *editor smell* (orphans, dangling `{{ref}}`s) rather than mirroring the server's `Flow.Validate()`, which is the source of truth at save time. - AIP Threads parent/branch invariants (US-374): every `Message` carries `ParentMessageID *int64` and `BranchID string` (default `"main"`). `MemoryStore.AppendMessage` and `pgAIPStore.AppendMessage` auto-link `ParentMessageID` to the last message on the same branch when the caller didn't supply one — preserving the linear-history contract for legacy callers that never set parent_message_id. Fork creates a fresh thread row, copies pivot's ancestor chain (root → pivot inclusive) into it under `branch_id='main'` with re-chained parents. PG fork uses a recursive CTE shape `JOIN aip_messages m ON m.id = (SELECT parent_message_id FROM aip_messages WHERE id = c.id)` — the parent column has to be re-projected via sub-select inside the recursive arm, NOT projected through the CTE itself. Tree builder `pkg/aip/handlers_fork.go::BuildMessageTree` is orphan-tolerant: a message whose parent id is absent from the slice surfaces as a root rather than being silently dropped (necessary because `ON DELETE SET NULL` may leave dangling pointers). To distinguish "pivot doesn't exist" from "pivot belongs to a different thread", `ForkThread` MUST sweep every thread's messages first then check ownership separately — collapsing both cases to NotFound mis-maps the HTTP error envelope.
- AIP Threads UI tree/branch view (US-375): `web/src/components/threads/ThreadsPage.tsx` exports `computeBranchPath(messages, tipId)` which walks `parentMessageId` from a tip up to root and is orphan-tolerant (terminates cleanly when the parent id points outside the slice). The tree panel filter is gated on `hasParentLinks` (any message in the slice has a parent id?) — if false, the filter is bypassed and the full message list renders. This is the SPA-side mirror of the backend's `MemoryStore.AppendMessage` auto-link semantics: legacy threads pre-US-374 ship messages without parent ids and must keep displaying as a flat chain. Apply the same gate-on-data-shape pattern when extending tree-aware UIs (branch picker, dataset transaction chain) — assume new schema columns may be absent on warm rows for some time after migration. `useSendAIPMessage` invalidates BOTH `aipQueryKeys.messages(threadId)` AND `aipQueryKeys.tree(threadId)` on success; encode dual invalidation in the hook so call sites stay one-line.
- Cell-level masking has TWO orthogonal axes (US-258 / US-376) that share one `cell_masks` table and one `pkg/cellsec.Engine`: (a) AppliesTo allow-list (legacy `MaskRule` lowercase hash/redact/partial), (b) CEL Expression predicate (`MaskStrategy` uppercase REDACT/HASH/NULL/PARTIAL with the new NULL strategy). Programs are pre-compiled once at `Engine.Reload` (and `SetMasks`) into a `compiledCellMask` wrapper so the per-row hot path is a flat map lookup + one `cel.Program.Eval`. The CEL bindings are `user.{id,email,roles,markings,attributes}` and `row.<property>` (the wire object's `Properties` map). The expression must return bool — TRUE means the mask fires (caller gets the masked value). Empty expression falls back to the legacy AppliesTo allow-list semantics. **Fail-closed contract:** any CEL eval error surfaces as "mask applies" so a broken expression never opens a hole in enforcement. The serialisation hook is `pkg/oss/service_impl.go::applyCellMasking` which now calls `Engine.CompileForRow(ctx, user, otRID, pk, row.Properties)` and dispatches via `masking.ApplyStrategyTransforms`. Legacy `Engine.Compile` still returns the old `map[string]MaskRule` shape for callers that don't have the row in scope.
- Pipeline incremental + schema-evolution (US-378) shares a fail-closed invariant: schema diff via `ResolveSchemaEvolution(prior, current)` MUST run BEFORE the source's `ReadAfter(ctx, after)` call. The runtime contract is "no side effects leak through a BREAKING_CHANGE": no read I/O, no sink schema extension, no row write. Future incremental connectors must seed their work through `pkg/pipeline/incremental.go::RunIncremental` so this ordering stays mechanically enforced. The `LatestCommittedOffset(ctx, pipelineID)` watermark filter is `status='success'` only — failed/canceled runs do NOT advance progress, otherwise a half-applied run could silently drop rows on the next APPEND. `pkg/pipeline/schema_evolution.go::typesEquivalent` is trim+case-insensitive for Type, case-sensitive on Name — schema sources frequently disagree on type casing without semantic difference, while column names ARE case-sensitive in most downstream stores.
- Column-level lineage (US-377) is a SECOND lineage surface alongside US-300's `lineage_edges`. The `lineage_column_edges` table tracks `(src_dataset, src_column) → (dst_object_type, dst_property)` and is populated synchronously by the datasource-binding write path: `OMSHandler.deriveColumnLineageOnBindingChange` calls `DeriveColumnLineageEdges(binding, properties)` and atomically `ReplaceColumnLineageForBinding`. Replace-by-binding (NOT append-only) is the canonical write semantics so a binding update that DROPS a property yields zero edges for it immediately. The `ColumnLineageStore` interface lives in `pkg/oms` (matching the `LineageStore` shape — narrow, off the main `Repository` interface so degraded-mode test routers don't have to cascade-stub it). `DeriveColumnLineageEdges` accepts BOTH wire shapes for `column_mapping` JSON: flat object `{propertyApiName: column}` AND array form `[{property, column}]` with `p`/`c` short-key alternates. Output is sorted lexicographically by (api_name, src_column) so identical mapping payloads produce identical edge sets modulo ts — useful for change-detection. Handler routes `GET /api/v2/lineage/property/{rid}` + `GET /api/v2/lineage/dataset-columns/impact?dataset=...&column=...` are mounted unconditionally on the lineage handler (404 ColumnLineageNotConfigured in degraded mode); both must appear in `api/openapi.yaml` AND `cmd/server/openapi_spec.yaml` because the contract test walks chi routes regardless of store wiring. Note: `datasource_bindings` admin routes were stripped in US-006 so the hook fires only via direct handler invocation today; the wiring is ready when admin routes return.
- Time-travel asOf (US-379 extends US-223): the OSS load handler's `?asOf=` query parameter now accepts TWO wire formats — RFC3339 timestamp (US-223 default) and `tx-<id>` reference into `dataset_transactions` (US-379). Branching lives in `pkg/oss/objectset/handler.go::resolveAsOf(ctx, raw)`; the `"tx-"` prefix routes to the wired `TransactionResolver` which translates to a `committed_at` instant, then both branches converge on `loadObjectsAsOf(time.Time)`. Resolver + history snapshot provider are intentionally orthogonal hooks — degraded-mode routers can wire one without the other. New asOf flavors (e.g. `branch:` refs) plug in as new prefix arms with zero changes downstream. The funnel consumer's `recordDatasetTransaction` lands one row per applied EditBatch with `parent_tx_id` resolved via `LatestForOntology(batch.OntologyAPIName)` — the chain is per-ontology, NOT per-ObjectType. `ON CONFLICT (tx_id) DO NOTHING` handles NATS at-least-once redelivery so a duplicate batch is silently deduped on the chain. `EditBatch.ID` is normalised via `strings.HasPrefix(id, "tx-")` and conditionally prepended; legacy publishers that emit raw uuids are still safe. The `tx_id` column on `object_history` is populated for future collision-disambiguation but the snapshot scan still uses `[valid_from, valid_to)` half-open intervals — same-instant batches fall back to "latest wins" until a future US wires tx-aware snapshot reads.
- WebSocket subscription cursor + replay (US-380): `pkg/subscriptions.EventLog` is the Hub-owned sliding-window replay buffer. Every `HandleObjectChange` and `HandleActionJobProgress` first calls `eventLog.Append` UNDER hub.mu and stamps the assigned monotonic cursor on the outbound `Message.Cursor` field. The lock ordering (append + index read in one critical section) guarantees that a subscription registered at hub.mu cannot miss an event whose cursor ≤ snapshot-time-latest AND will receive every live event with cursor > snapshot-time-latest. Aggregation events are NOT logged — they are derived per-subscription state and reseed via Bleve at subscribe time. Reconnect protocol: `?since=<cursor>` is parsed BEFORE `websocket.Accept` so a malformed value can be coerced to 0 ("no replay"). The welcome envelope carries `lastEventId = eventLog.LatestID()`. If `since < earliestLive` OR `since > latest` the connection-level `onOutOfDate` (no SubscriptionID) fires immediately and `replayCursor` is set to -1 to disarm per-subscription replay. Otherwise each subscribe handler — `handleSubscribe` / `handleSubscribeObjectSet` / `handleSubscribeActionJob` — drops the `defer Unlock` pattern in favour of explicit locks so it can register the subscription, release locks, then drain `replayObjectSubscription` / `replayActionJobSubscription` onto `c.send`. Because the routing index is updated under the same hub.mu critical section as the snapshot read, there's no overlap between replayed events (id ≤ snapshot.maxID) and live events (id > snapshot.maxID). Pattern: when adding new event kinds that need replay support, give them a new `EventLogEntry.Kind` discriminator + a marshaller method on the entry, then thread them through the replay drain alongside the existing `objectChange` / `actionJobProgress` arms.

## 2026-05-02 - US-366 - searchAround 多跳与 cycle detection

**Implementation:**
- `pkg/oss/objectset/executor.go::executeSearchAroundPath` now maintains a cross-hop `visited` set keyed by `(objectType, primaryKey)` (canonical helper `visitedKey`). The set is seeded with the inner ObjectSet's PKs so paths that step back to the origin (A→B→A direct loop) shrink to zero on hop 2. After each hop's resolver call the executor dedups within the hop, then prunes any PKs already present in `visited`, then records the survivors in `visited` for subsequent hops. Triangle / longer cycles (A→B→C→A) terminate cleanly with an empty result instead of re-walking the source.
- New constant `SearchAroundIntermediateCap = 1_000_000` and sentinel `var ErrQueryTooLarge` (wraps the literal `WEAVE_QUERY_TOO_LARGE` marker). The walk aborts when either the seed set OR any post-prune intermediate set exceeds the cap; the wrapped error carries the offending hop index, link API name and the actual size for caller diagnostics.
- `pkg/apierror/error.go::NewQueryTooLarge` produces the new wire-format code `WEAVE_QUERY_TOO_LARGE` at HTTP 422.
- `pkg/oss/objectset/handler.go::executeError(err)` is the single chokepoint for executor → APIError translation: it special-cases `errors.Is(err, ErrQueryTooLarge)` → 422 and falls back to the historical `INVALID_ARGUMENT "ObjectSetFailed"` envelope. All four call sites in the package (handler.go LoadObjects + Aggregate, handler_preview.go Preview, snapshot_persisted.go CreateSnapshot) now route through it. The `loadLinks` legacy single-link surface in handler_objectset.go was left on its existing `LoadLinksFailed` envelope because it never triggers the path-traversal cap.
- `pkg/oss/objectset/searcharound_us366_test.go` adds 4 unit tests (direct A→B→A loop, A→B→C→A triangle, fresh-PK regression, 1M+1 oversize abort) plus `BenchmarkExecute_SearchAround_Path_ThreeHops_10K`. Bench rooted at `Type:"static"` so it isolates the path-traversal cost (visited-set + dedup + resolver dispatch) without Bleve overhead.

**Learnings for future iterations:**
- The `executeSearchAroundPath` visited set is keyed by `(objectType, pk)` not just `pk`, because path traversals legitimately revisit the *same PK string* at *different ObjectTypes* (e.g. a numeric "1" PK appearing as both Order and Customer). A pk-only key would over-prune. The NUL-separator (`"\x00"`) is safe — Weave's RID format and ObjectType API names disallow NUL.
- Cycle detection seeds `visited` with the inner ObjectSet PKs at the inner set's ObjectType. This means the previous behaviour where reverse traversal returned the seed verbatim (e.g. employee→dept→reverse-employee yielded the original employee) is now suppressed. One existing test (`TestExecute_SearchAround_Path_MixedDirection`) had to be updated — the expected return set is now the *peers* of the seed, not the seed itself. If you find more callers that depend on "starting object echoed back", document it as a usage migration, not a regression.
- Intermediate cap of 1M is generous on purpose — typical fanouts in northwind / chinook stay sub-100K. The cap exists primarily to break runaway resolvers (e.g. a misconfigured M2M link returning the cartesian join). Surface a clear `cap` parameter in the APIError so SDK users know what threshold they tripped.
- Bench rule of thumb: when `Type:"base"` is the inner set, `searchReq.Size = BaseExecutionCap (10000)` against an in-memory Bleve index can hang for minutes per iteration. Use `Type:"static"` with a pre-built PK slice to isolate the searchAround executor's own cost. If you actually want to bench Bleve+searchAround end-to-end, allocate a real disk-backed index and seed in batches.
- The `executeError` helper in `pkg/oss/objectset/handler.go` is the new chokepoint for executor → APIError translation. Before adding a new typed executor error, define the sentinel in `executor.go`, add the `apierror.New<Code>` constructor in `pkg/apierror/error.go`, and route through `executeError`. Don't rebuild the switch ladder per handler.
- `loadLinks` (handler_objectset.go) wraps a single-link searchAround so it cannot trip the path-traversal cap. Leaving it on its existing `LoadLinksFailed` envelope is intentional; promoting it to `executeError` would just add an unused branch.

**Learnings for future iterations:**
- `tdigest.NewWithCompression(100)` is the right knob for hitting the PRD's "1M points ≤ 16 KiB" memory budget. Default compression `1000` blows past 160 KiB. The library's centroid struct is two `float64`s (16 B), and the only structural caps are `2c` processed + `8c` unprocessed. Multiply by 16 to get the upper-bound footprint; the cumulative slice (≤ `2c+1` float64s) is the only meaningful add-on after `process()` runs.
- For unit-weight centroids (every bucket smaller than `2c`), t-digest's `Quantile` is *linear interpolation between two consecutive sorted values at half-integer cumulative weights* — i.e., for `index = q·n`, `lower = ceil(index − 0.5)`, result = `(z2·v[lower-1] + z1·v[lower]) / (z1 + z2)` where `z1 = index − (lower − 0.5)`, `z2 = (lower + 0.5) − index`. Any test that wants to compare against an exact reference at small N must use this same convention; nearest-rank disagrees by a full bucket on small N (Argentina N=16 at p95: nearest-rank → sorted[15] vs t-digest → 0.3·sorted[14] + 0.7·sorted[15]).
- The HdrHistogram dependency disappears entirely after this story. `go mod tidy` removes it from `go.mod`/`go.sum`. Future iterations don't need the `percentileScale = 1000.0` shift/scale dance — t-digest accepts any float64 (including negatives) directly without preprocessing.
- The `TestApproximatePercentile_OneMillion_*` accuracy and memory gates are gated by `testing.Short()` so `go test -short` skips them, but `go test ./...` (the default) runs them. They take ~150 ms total — cheap enough to keep in the regular test path rather than -bench-only.
- `digestFootprint(td)` is a deterministic upper-bound calculation rather than a runtime.MemStats delta, because allocator noise on `runtime.MemStats` made the latter approach non-portable. The accounting matches the library's slice/struct layout: processed cap × 16 B + maxUnprocessed cap × 16 B + (len(processed)+1) × 8 B + struct overhead.
- `BenchmarkApproxPercentileTDigest_OneMillion` at b.N=1 measures the entire 1M-point ingest + Quantile cost, which makes per-op numbers dominated by allocator + sort time. If you need fine-grained Add-only timing, refactor to allocate the digest once outside the b.N loop and call `Add` inside; current bench keeps the e2e shape so the 78 ms/op is "what a real query would cost".

Unknown callees (lookup returns `ErrNotFound`) are skipped — the runtime surfaces "function not found" at execute time. Already-fully-walked subtrees are memoised so DFS stays O(N+E).

- The runtime injection half of US-371 was DONE in US-220 — `weave.callFunction(ref, params)` registered via `pkg/functions/goja_shim_functions.go::registerWeaveShim` with depth + cycle guards in `pkg/functions/fncall`. Future US that touch function-to-function dispatch (saga steps, AIP tools, etc.) should reuse the same `fncall.WithFrame(ctx, ref)` seeding pattern so depth/cycle invariants hold uniformly.
- Static cycle detection MUST use a "publish-time overlay" — the in-flight row's NEW source code overrides what the repo would return for the same identity. Without this an UpdateFunction that adds a cycle (B already calls A; you UPDATE A to call B) slips through because the repo still has the cycle-free A. Pattern: a small adapter struct that satisfies the lookup interface and short-circuits `(name, version)` / RID matches to the in-flight Function. Reusable for any future "scan before persist" path (action saga step graphs, automation-rule chains, etc.).
- The regex scanner is intentionally regex-based, not goja AST. JS parsers add ~MB of binary weight and dispatch overhead; the literal `weave.callFunction("ref"` shape is regex-trivial and the runtime catches dynamic cases anyway. The cost: dynamic refs (variables, templates) are invisible at publish time. - `stripJSCommentsAndStrings` operates byte-for-byte and preserves length so any byte offset in the scrubbed source matches the original — leave that invariant in place if a future reviewer wants to surface exact line numbers from the regex match. - `canonicalRefForFunction(fn) = name@NormalisedVersion()` (or RID when name is empty) is the identity collapsing key. This means a callee referenced by RID and the same callee referenced by name still register as the same DFS node — necessary because authors mix the two ref shapes liberally (RIDs in code-generated bindings, names in hand-written scripts). Don't switch to a pk-only key without thinking through the cross-shape collision case.
- The PRD's named codes `FUNCTION_RECURSION_DEPTH_EXCEEDED` / `FUNCTION_CALL_CYCLE` were embedded in TWO places: (a) the runtime panic-string prefix in `goja_shim_functions.go` so the JS-side error message includes the named code, AND (b) the apierror constructors for handlers that map sentinel → 422. The runtime route still preserves `errors.Is(err, fncall.ErrDepthExceeded)` for typed dispatch — adding the prefix is additive, not breaking.

**Learnings for future iterations:**
- `aip.Message` is the second AIP struct after `aip.Thread` to accept a nilable `*int64` JSON field. The Go JSON encoder renders `*int64=nil` as `omitempty` only when the field is tagged that way — without `omitempty` the wire shape would emit `"parentMessageId": null` and force every legacy SDK consumer to treat null as a meaningful state. Use `*int64` + `json:",omitempty"` whenever the field is genuinely tri-state (nil = no parent / set = parent id) instead of a sentinel int like 0 or -1.
- `ForkThread` MUST distinguish "pivot doesn't exist anywhere" from "pivot exists but in a different thread". A naïve implementation that builds a `byID` map only over `s.messages[srcThreadID]` collapses both cases to `ErrMessageNotFound`, which then surfaces as 404 to the SDK. The fix is a two-stage walk: sweep every thread's slice first to locate the pivot, then check `pivot.ThreadID == srcThreadID` separately. The HTTP layer already maps `ErrMessageNotFound → 404` and `ErrPivotThreadMismatch → 400`, so getting this right at the store keeps the contract crisp.
- The PG `ForkThread` recursive CTE was the trickiest piece. The naïve `WHERE id = c.parent_message_id` join doesn't compile in postgres because `c` doesn't see future iterations of itself; the working pattern is `JOIN aip_messages m ON m.id = (SELECT parent_message_id FROM aip_messages WHERE id = c.id)` — i.e., the recursive arm queries the parent column in a sub-select rather than projecting it through the CTE. `ORDER BY depth DESC` delivers the chain root-first so the re-insert loop can chain forward without a second walk.
- `MemoryStore.AppendMessage` now auto-links `ParentMessageID` to the last message on the same branch when the caller didn't pass one. This is critical for backwards compatibility with US-279 / US-284 callers that never set parent_message_id — without it every legacy linear thread would be a forest of disconnected roots in the new tree view. The PG store mirrors the same auto-link via a `SELECT id ... ORDER BY id DESC LIMIT 1`. Don't break this contract: future changes to the message schema should preserve the "no parent supplied → autolink to last" semantics so the tree view remains coherent.
- Fork's title default `"<src> (fork)"` is a UX lubricant, not an invariant — overrides via the `title` field in the request body win unconditionally. The provider is *not* overridable on fork by design (switching mid-branch would invalidate tool_call ids referenced earlier in the chain), but model and system prompt are because they're plain text the LLM treats per-turn. If a future US adds branch-id columns *to threads* (so a thread can carry multiple branches in-place rather than spawning new threads), revisit whether provider becomes per-branch — for now the "one provider per thread" invariant from US-279 is preserved.
- The `MessageTreeNode.Message *Message` pointer-embed is the right shape for SDK serialisers because it flattens the message fields onto the node JSON without a wrapper key. The alternative (named field `message: Message`) would force the SPA to write `node.message.id` everywhere — a worse UX. Document this in the SDK README when US-375 (UI tree browse) lands.
- AIP routes still don't need OpenAPI entries (per the US-373 / US-281 contract-test gate) because the contract test deps leave `AIPStore = nil`. If a future US wires a non-PG AIP store into the contract router, every AIP route will simultaneously need OpenAPI entries — plan for an "OpenAPI bulk add" PR at that point rather than incremental updates per US.

**Learnings for future iterations:**
- The PRD wording "pipeline_runs 表新增 last_committed_offset BIGINT" describes one column add but the full design needs THREE schema additions: the offset column on `pipeline_runs` (the per-run watermark), `pipelines.mode` (the runtime switch — 'APPEND' opts in, '' / 'FULL' keeps legacy semantics), and `pipelines.last_known_schema` (the persistent schema snapshot the diff compares against). Without the second schema-state column the schema diff has nothing to compare against on a fresh run and the BREAKING_CHANGE gate is dead code. Pattern: when a PRD describes a single column on a runs table for "incremental progress", check whether the *pipeline* row itself needs sibling state columns (config + cumulative state) — usually it does.
- `LatestCommittedOffset` MUST filter on `status='success'` — failed/canceled runs that were halfway through processing do NOT advance the watermark. A failed run at offset=200 with rows already partially written (some sinks are at-most-once, some at-least-once) cannot be "trusted" as committed; the next APPEND must re-read from the prior successful watermark to avoid silently dropping rows. Tests assert this with the `success/failed/success @ 100/200/150` shape — the result is 150 (max across successes), NOT 200 (max across all).
- The schema-evolution gate runs BEFORE any source read, on purpose. If the diff aborts mid-run (after rows have been ReadAfter'd), the source has already paid the read cost and may have advanced its own client-side cursor — wasted I/O AND a stale runtime state. By calling `Source.Schema(ctx)` first and resolving the diff against `pipelines.last_known_schema` before `Source.ReadAfter(ctx, ...)`, a BREAKING_CHANGE rejects the run cheaply. The `TestUS378_SchemaDiff_DroppedColumnReturnsBreakingChange` test asserts `src.readCount == 0` after the abort to lock this contract in.
- `MergeSchema` preserves the prior column order on purpose. Bleve facet positions, downstream Parquet schema ordering, and any client that consumes schema-positional offsets all benefit from a stable column ordering across runs. New columns append in observed order so a single-run schema rewrite is impossible — only ADD operations are allowed at evolution time, never REORDER.
- `typesEquivalent(a, b)` uses `strings.EqualFold(strings.TrimSpace(a), strings.TrimSpace(b))` because real-world schema sources mix `Long`/`long`/`LONG` and sometimes ship trailing whitespace from CSV-style sources. Case-sensitive equality would surface every cosmetic difference as a BREAKING_CHANGE conflict, blocking legitimate runs. The tightening is in *Name* matching (case-sensitive) — column names ARE case-sensitive in most downstream stores, while their type tags are not.
- The Defensive `filterAboveOffset(rows, cutoff)` re-filter in `RunIncremental` is intentional even though `IncrementalSource.ReadAfter` already promises "Offset > after" — connectors that filter client-side (e.g., a CSV connector that reads everything then filters) might leak rows below the watermark on a buggy implementation. The re-filter is a single pass over the slice; the cost is negligible compared to the safety gain.
- The `IncrementalSink` interface is intentionally optional (nil = preview mode). This unblocks two future US directions: (a) a "dry-run" pipeline preview UI that resolves the diff + reports the row delta without writing, (b) an "audit" run that captures the schema evolution history into a separate audit-only sink without touching the production index. Both can be built on `RunIncremental(ctx, opts)` without an interface change.
- `pkg/pipeline/incremental.go` is named at the package root (not under `pkg/pipeline/incremental/...`) because it's the new opt-in execution mode for the existing pipeline runner, not a separate service. The `Run*` API surface lives next to `RunDAG` so callers see both shapes when reading the package. If a future US adds CDC-style streaming, that's where a sibling `pkg/pipeline/streaming.go` would land — by mode, not by transport.
- The Store interface widening to add `LatestCommittedOffset` is backwards-compatible because all existing callers (handlers, scheduler) don't touch APPEND-mode state. New methods in interface go at the BOTTOM of the existing block grouped by US — easier to read the chronological evolution of the interface, and the `// US-298 — ... API.` / `// US-378 — ...` comments serve as section headers for future additions.

**Learnings for future iterations:**
- US-379's "?asOf=tx-..." parameter shares the existing US-223
  `?asOf=` query param rather than introducing a separate
  `?asOfTx=`. The resolveAsOf helper branches on the `"tx-"` prefix
  to pick the resolver path, then both branches converge on the same
  `loadObjectsAsOf(time.Time)` body. This keeps the time-travel
  pipeline single-shape and lets future asOf flavors (e.g. branch
  refs) plug in as new prefix arms — `tx-`, `branch:`, etc. — with
  zero changes to the snapshot scan.
- The funnel consumer's tx-id stamping is the correctness backstop
  for batches that share a millisecond-level recorded_at. The
  US-223 `[valid_from, valid_to)` half-open interval scan correctly
  selects exactly one row per PK when timestamps are distinct, but
  collapses two same-instant batches to "always return the latest"
  (the earlier row's `valid_to` equals its own `valid_from`, making
  the interval empty for any T at that instant). The `tx_id`
  back-reference column lets a future US-379+ enhancement
  disambiguate by tx — for now the column is populated but
  unconsumed by the snapshot query, since single-machine deployments
  rarely emit colliding-timestamp batches.
- `EditBatch.ID` may or may not already carry the `tx-` prefix
  depending on the publisher (some action paths prefix, some emit
  raw uuids). The `recordDatasetTransaction` helper canonicalises
  via `strings.HasPrefix` + conditional prepend so the
  dataset_transactions table is always queryable by the
  publishe-r-agnostic prefix. Tests cover both shapes.
- `ON CONFLICT (tx_id) DO NOTHING` on the tx_id PK is the
  redelivery contract: NATS guarantees at-least-once, so a duplicate
  EditBatch will redrive `applyBatchWithHistory` and try to record
  the same tx_id twice. Without the `DO NOTHING` clause the second
  RecordDatasetTransaction would return a unique-violation error
  the consumer would then log as a false alarm — and worse, abort
  the host code path that surfaces the txID for object_history
  stamping. Pattern: any new "one-row-per-EditBatch" persistence
  hook that runs from the funnel consumer needs this idempotency
  clause, OR the consumer must re-read the existing row and
  short-circuit. Idempotent INSERT is the simpler choice here.
- `objectset.TransactionResolver` is decoupled from
  `objectset.HistorySnapshotProvider` so a deployment can wire one
  without the other. Specifically: degraded-mode test routers
  without PG keep the timestamp-based asOf path live (HistorySnapshotProvider
  resolves an in-memory map) without surfacing a tx-id resolver,
  and the handler refuses tx-id lookups with
  `TransactionLookupUnavailable` rather than tripping over a nil.
  Pattern: when adding a new wire format to an existing query
  parameter, keep the resolver / provider hooks orthogonal —
  callers should be able to mix-and-match without scaffolding stub
  implementations.
- `/api/v2/datasets/{rid}/history` is a top-level route (NOT
  nested under `/api/v2/ontologies/{ontology}/`) because the
  PRD-mandated path is `/datasets/{rid}/history` and the chain is
  per-ontology — `{rid}` IS the ontology identifier, so nesting
  would be redundant. Pattern: when a PRD acceptance criterion
  specifies a URL shape, prefer the literal shape over inferring
  the chi router pattern from sibling endpoints. The tradeoff is
  one extra `GetOntology` lookup at request time vs. a chi
  middleware-resolved ontology context. The lookup pays for itself
  by accepting BOTH RID and api name as `{rid}`, matching how
  every other "rid-or-name" endpoint already behaves.
- The `historyCap = 1000` constant in the dataset history handler
  is intentional and documented inline — single-machine deployments
  rarely accumulate more than a few hundred batches per ontology
  before someone snapshots / archives. If pagination becomes
  necessary the path forward is `?pageToken=` cursor (mirroring
  loadObjects) rather than uncapping. Don't add pagination
  pre-emptively — measure first.

## 2026-05-03 - US-380 - WebSocket subscription cursor + replay

**Implementation:**
- `pkg/subscriptions/eventlog.go` (new): `EventLog` is a sliding-window
  FIFO of recently dispatched events keyed by a monotonic int64 cursor.
  `Append(entry)` returns the assigned cursor under a mutex so callers
  can stamp it on the outbound wire message in lockstep. `Snapshot(since)`
  returns the tail (entries with id > since) defensively copied for
  iteration without the lock. Eviction is `Window` OR `MaxEntries`
  (whichever fires first); defaults are 5 minutes / 10000 entries per
  the PRD. `EventLogEntry.Kind` discriminates `objectChange` vs
  `actionJobProgress`; aggregation events are NOT logged because they
  are per-subscription derived state and re-seed via Bleve at
  subscribe time. Marshal helpers on the entry produce the same JSON
  shapes that `HandleObjectChange` / `HandleActionJobProgress` would
  emit live, so replay drains never diverge from live dispatch.
- `pkg/subscriptions/hub.go`: `Message` envelope gains `Cursor int64`
  (per-event id, JSON `cursor`) and `LastEventID int64` (welcome
  high-water mark, JSON `lastEventId`). `HubConfig` gets an embedded
  `EventLogConfig`. `Hub` owns one `*EventLog` plus an exported
  `EventLog()` accessor for tests. `Connection.replayCursor` (int64)
  carries the parsed `?since=` value through to the subscribe
  handlers; `0` means no replay requested, `-1` is the post-out-of-window
  sentinel. `parseSinceCursor(raw)` is the URL parser — empty / negative /
  malformed all coerce to 0 so a bad client never fails the upgrade.
- `HandleWSWithUser` now reads `?since=<cursor>` BEFORE `websocket.Accept`,
  stamps the live high-water cursor on the welcome envelope, and emits
  a connection-level `onOutOfDate` (no SubscriptionID) if the requested
  cursor falls outside `[earliestLive, latest]`. The out-of-window
  branch zeros `replayCursor` (-1) so subsequent subscribes do not
  attempt per-subscription replay.
- `pkg/subscriptions/subscription.go::HandleObjectChange` and
  `pkg/subscriptions/job.go::HandleActionJobProgress` now `Append` to
  the log under `hub.mu` BEFORE reading the routing index, then stamp
  the assigned cursor on the outbound `objectChanged` /
  `actionJobProgress` messages. The single critical section guarantees
  the snapshot/index ordering invariant: subscriptions registered at
  hub.mu cannot miss events whose cursor ≤ snapshot.maxID, AND replay
  + live dispatch never deliver the same event twice (replayed cursors
  are bounded above by snapshot.maxID; live cursors are strictly above).
- `pkg/subscriptions/aggregation.go::sendAggregationChanged` widened to
  accept the triggering cursor; subscribe-time initial snapshots use
  cursor=0 (not associated with any specific log entry).
- `pkg/subscriptions/replay.go` (new): `replayObjectSubscription` and
  `replayActionJobSubscription` are the per-subscription drains. Both
  walk a snapshot of the log since the connection's `replayCursor`,
  filter by the subscription's match function (pure-data
  `Subscription.matches` for objects, JobID equality for jobs),
  marshal each entry as the equivalent live message, and push to
  `c.send` with the entry's original cursor preserved. `c.markOverflow(subID)`
  + early return on a full send buffer keeps replay polite under
  back-pressure (existing `onOutOfDate` overflow path then surfaces).
- `pkg/subscriptions/subscription.go`, `objectset.go`, and `job.go`
  subscribe handlers: dropped the `defer h.mu.Unlock()` /
  `defer c.subMu.Unlock()` pattern in favour of explicit locks so we
  can release before draining replay onto `c.send` (replay enqueues
  messages and must not contend with `hub.mu` / `conn.subMu`). When
  `replayCursor > 0` the handler emits the `subscribed` reply directly
  to `c.send`, drives the appropriate replay function, and returns the
  Message{} sentinel that tells the readPump to skip the default
  dispatch.

**Learnings for future iterations:**
- The replay-and-routing-index invariant turns on doing the log
  `Append` and the `subIndex[objectType]` read in the SAME critical
  section. If the append moves out of the lock, a subscription that
  arrives between append and dispatch can both miss the live event
  AND replay it (because the replay snapshot would not include the
  un-stamped event). Pattern: any new event kind that needs replay
  must follow the same hub.mu append-then-route shape as the existing
  two paths. Don't optimise the lock window away.
- The subscribe handlers had to drop `defer Unlock()` in favour of
  explicit locks because the replay drain enqueues messages onto
  `c.send` and `c.send` is a buffered channel — under load (or in
  tests with a deliberately small buffer) the replay can briefly
  block on the writePump, and we must not be holding hub.mu during
  that wait. The aggregation subscribe handler had already adopted
  the explicit-lock pattern for the same reason; this story aligns
  the other three handlers with that convention.
- Out-of-window detection happens at handshake time, NOT at
  subscribe time. The reasoning: the client should know to refresh
  global state BEFORE re-establishing subscriptions, otherwise it
  will paint a partial view from `subscribed` → `objectChanged` and
  only later discover the gap. The connection-level `onOutOfDate`
  with empty SubscriptionID is the documented signal for "everything
  you knew is stale; do a full refresh and re-subscribe from scratch".
- `?since=<cursor>` parsing is deliberately liberal — empty /
  negative / non-numeric / scientific-notation all coerce to 0 ("no
  replay"). The connection still upgrades cleanly. This is the
  natural extension of the rest of the websocket layer's policy
  ("don't let bad client input fail the connection") and matches
  how SSE Last-Event-ID handling already behaves elsewhere in the
  codebase. If a future story needs to surface "your cursor was
  malformed" to the client, add a fresh out-of-band notice rather
  than failing the upgrade.
- `EventLog.Snapshot(since)` returns `entries, minLive` so callers
  who care about the out-of-window verdict get both pieces atomically.
  At present `HandleWSWithUser` consults `EarliestID()` and
  `LatestID()` separately because the welcome path branches on each
  bound, but the unified accessor is there for future SDK helpers
  that want a single round-trip ("am I in the window?") API.
- Aggregation events not entering the log is a deliberate design
  choice: per-subscription derived state (running totals, group
  buckets) cannot replay correctly from a wire envelope; the only
  safe recovery is to re-seed via Bleve at subscribe time. If
  aggregation subscribers need replay-style continuity in the
  future, the right move is to carry a `lastSeenAggregationVersion`
  field on the subscription itself rather than logging the
  individual `aggregationChanged` payloads.
- Tests inject `EventLog.nowFunc` (private field) to simulate
  multi-second outages without sleeping. Pattern: keep the
  injection point package-private (not on `EventLogConfig`) so
  production code cannot accidentally drive it; tests in the same
  package retain access. Existing US-133/308 tests follow the same
  convention with `Connection.nowFunc` for rate-limit windows.
