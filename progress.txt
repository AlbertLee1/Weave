## Codebase Patterns
- ObjectSet snapshot subsystem has TWO distinct surfaces: (1) the in-memory `pkg/oss/objectset.Store` keyed by `createTemporary` RIDs (1h TTL), and (2) the durable `object_set_snapshots` table written via the `PersistedSnapshotStore` interface (US-224). The PG row interface lives in `pkg/oms` (`ObjectSetSnapshot` + `ObjectSetSnapshotStore`); the direction-of-dependency rule keeps `pkg/oms` from importing `pkg/oss/objectset`, so `cmd/server/object_set_snapshot_adapter.go` bridges them.
- A third durable surface — `saved_object_sets` (migration 000013) — is fully implemented (`pkg/oss/objectset/PGSavedStore`) but NOT YET wired into `cmd/server`. It has unit + integration tests but no HTTP route. New work that needs durable saved definitions can wire the existing store; no new schema is needed.
- Migration numbering convention: zero-padded `000NNN_description.{up,down}.sql`. Migrations are run with `golang-migrate`. As of US-365 the tip is migration 000082.
- Test build tags: unit tests run by default; `//go:build integration` tests need `go test -tags integration` and use `internal/testutil.StartPGContainer(t)` to boot a real Postgres container. The `ListEntries` helper on the in-memory `Store` is the canonical way to introspect ephemeral entries from tests.
- For canonical-JSON hashing across the codebase, prefer the `objectset.HashDefinition` helper (sorts keys, sha256 hex). Calling `json.Marshal` first is fine — the helper canonicalises again.
- Executor errors that need a non-default APIError mapping should be sentinels in `pkg/oss/objectset/executor.go` (e.g. `ErrQueryTooLarge`) and translated by the `executeError(err) *apierror.APIError` helper in `pkg/oss/objectset/handler.go`. All `h.executor.Execute` callers in this package go through that helper instead of hand-rolling `apierror.NewInvalidParameter("ObjectSetFailed", …)`. Add an `apierror.New<Code>` constructor in `pkg/apierror/error.go` for the wire-format code (e.g. `WEAVE_QUERY_TOO_LARGE` → 422).
- `pkg/oss/objectset/searcharound_path_test.go::seedMultiHopIndex` accepts `testing.TB` so unit tests AND benchmarks can share it. `multiHopResolver` is the canonical in-memory `LinkResolver` for path-traversal tests — it implements `ResolveLinkedObjectsByAPIName` (forward), `ResolveLinkedReverseByAPIName` (reverse), `ResolveTargetObjectType` and `ResolveTargetObjectTypeDir`. Bench paths should root at `Type:"static"` rather than `Type:"base"` to bypass Bleve in measurement loops; `Type:"base"` with the 10K cap can hang the in-memory Bleve index.
- `aggregation.AggregationRequest.Accuracy` is the Palantir-style request-level toggle (`ALLOW_APPROXIMATE` default, `REQUIRE_ACCURATE` opt-in). `computeMetrics(idx, baseQuery, specs, accuracyMode)` is the chokepoint that routes `approximateDistinct` → exact and `approximatePercentile` → sort-based exact when `REQUIRE_ACCURATE` is set. The fourth return value (`approximate bool`) flags when an approximate algorithm actually fired so the response.accuracy column reflects runtime truth, not just user intent. When adding a new approximate aggregation, route both the exact-fallback path AND the approximate-flag bookkeeping through this helper rather than emitting accuracy from the call site.
- HLL sparse-exact threshold: `1<<(precision-2)` (4096 at default p=14). Below this cardinality the axiomhq sketch is in its sparse compressed-list mode and returns byte-exact counts; above it transitions to dense estimation. Use `sparseExactThreshold(precision)` from `bleve_agg.go` rather than hard-coding the boundary, so a future precision change keeps the response.accuracy verdict consistent.
- `approximatePercentile` runs through `pkg/oss/aggregation/tdigest_percentile.go` (influxdata/tdigest) at compression `DefaultTDigestCompression=100`. That cap is the steady-state memory contract: max processed centroids `2c` + max unprocessed `8c` ≈ 16000 bytes ≤ 16 KiB ceiling (tested at 1M points). When a bucket has unit-weight centroids (any size below the digest's processed cap), Quantile reduces to *linear interpolation between two flanking sorted values at half-integer cumulative weights* — disagrees with HdrHistogram's nearest-rank/3-sig-fig convention, so any percentile reference test must use the same interpolation formula (see `phase6_percentile_groupby_test.go::referencePercentileForBucket`). HdrHistogram is no longer in the dependency graph.

- AIP Threads parent/branch invariants (US-374): every `Message` carries `ParentMessageID *int64` and `BranchID string` (default `"main"`). `MemoryStore.AppendMessage` and `pgAIPStore.AppendMessage` auto-link `ParentMessageID` to the last message on the same branch when the caller didn't supply one — preserving the linear-history contract for legacy callers that never set parent_message_id. Fork creates a fresh thread row, copies pivot's ancestor chain (root → pivot inclusive) into it under `branch_id='main'` with re-chained parents. PG fork uses a recursive CTE shape `JOIN aip_messages m ON m.id = (SELECT parent_message_id FROM aip_messages WHERE id = c.id)` — the parent column has to be re-projected via sub-select inside the recursive arm, NOT projected through the CTE itself. Tree builder `pkg/aip/handlers_fork.go::BuildMessageTree` is orphan-tolerant: a message whose parent id is absent from the slice surfaces as a root rather than being silently dropped (necessary because `ON DELETE SET NULL` may leave dangling pointers). To distinguish "pivot doesn't exist" from "pivot belongs to a different thread", `ForkThread` MUST sweep every thread's messages first then check ownership separately — collapsing both cases to NotFound mis-maps the HTTP error envelope.
- AIP Threads UI tree/branch view (US-375): `web/src/components/threads/ThreadsPage.tsx` exports `computeBranchPath(messages, tipId)` which walks `parentMessageId` from a tip up to root and is orphan-tolerant (terminates cleanly when the parent id points outside the slice). The tree panel filter is gated on `hasParentLinks` (any message in the slice has a parent id?) — if false, the filter is bypassed and the full message list renders. This is the SPA-side mirror of the backend's `MemoryStore.AppendMessage` auto-link semantics: legacy threads pre-US-374 ship messages without parent ids and must keep displaying as a flat chain. Apply the same gate-on-data-shape pattern when extending tree-aware UIs (branch picker, dataset transaction chain) — assume new schema columns may be absent on warm rows for some time after migration. `useSendAIPMessage` invalidates BOTH `aipQueryKeys.messages(threadId)` AND `aipQueryKeys.tree(threadId)` on success; encode dual invalidation in the hook so call sites stay one-line.
- Cell-level masking has TWO orthogonal axes (US-258 / US-376) that share one `cell_masks` table and one `pkg/cellsec.Engine`: (a) AppliesTo allow-list (legacy `MaskRule` lowercase hash/redact/partial), (b) CEL Expression predicate (`MaskStrategy` uppercase REDACT/HASH/NULL/PARTIAL with the new NULL strategy). Programs are pre-compiled once at `Engine.Reload` (and `SetMasks`) into a `compiledCellMask` wrapper so the per-row hot path is a flat map lookup + one `cel.Program.Eval`. The CEL bindings are `user.{id,email,roles,markings,attributes}` and `row.<property>` (the wire object's `Properties` map). The expression must return bool — TRUE means the mask fires (caller gets the masked value). Empty expression falls back to the legacy AppliesTo allow-list semantics. **Fail-closed contract:** any CEL eval error surfaces as "mask applies" so a broken expression never opens a hole in enforcement. The serialisation hook is `pkg/oss/service_impl.go::applyCellMasking` which now calls `Engine.CompileForRow(ctx, user, otRID, pk, row.Properties)` and dispatches via `masking.ApplyStrategyTransforms`. The runtime contract is "no side effects leak through a BREAKING_CHANGE": no read I/O, no sink schema extension, no row write. Future incremental connectors must seed their work through `pkg/pipeline/incremental.go::RunIncremental` so this ordering stays mechanically enforced. The `LatestCommittedOffset(ctx, pipelineID)` watermark filter is `status='success'` only — failed/canceled runs do NOT advance progress, otherwise a half-applied run could silently drop rows on the next APPEND. `pkg/pipeline/schema_evolution.go::typesEquivalent` is trim+case-insensitive for Type, case-sensitive on Name — schema sources frequently disagree on type casing without semantic difference, while column names ARE case-sensitive in most downstream stores.

- App publish/share owner-vs-viewer split (US-396): `pkg/apps` was previously fully owner-private (every Get/Update/Delete passes `ownerID` and the store maps non-owners to `ErrNotFound`). US-396 introduces the first viewer-facing surface: `Store.GetPublished(ctx, rid)` drops the owner gate entirely and is wired to `GET /api/v2/apps/{rid}/view` behind `requireAuth` only. Re-publishing advances the pin to `apps.version`; Update WITHOUT re-publish leaves `/view` stuck on the previously-pinned snapshot (this is the read-only contract, validated end-to-end in `TestHandler_PublishViewIntegration_PinsSnapshotAcrossUpdates`). Pattern: when extending other owner-private surfaces (dashboards, comment threads) into "shared with viewers" territory, follow this layering — a NEW handler that drops the owner gate AND a new sentinel for "viewer can see the resource exists but it's not currently shared" rather than collapsing to NotFound. The all-or-nothing CHECK constraint is the right canonical pattern for any future multi-column status block (`archived_at + archived_by`, `locked_at + lock_holder`, etc.).
- WebSocket subscription cursor + replay (US-380): `pkg/subscriptions.EventLog` is the Hub-owned sliding-window replay buffer. Every `HandleObjectChange` and `HandleActionJobProgress` first calls `eventLog.Append` UNDER hub.mu and stamps the assigned monotonic cursor on the outbound `Message.Cursor` field. The lock ordering (append + index read in one critical section) guarantees that a subscription registered at hub.mu cannot miss an event whose cursor ≤ snapshot-time-latest AND will receive every live event with cursor > snapshot-time-latest. Aggregation events are NOT logged — they are derived per-subscription state and reseed via Bleve at subscribe time. Reconnect protocol: `?since=<cursor>` is parsed BEFORE `websocket.Accept` so a malformed value can be coerced to 0 ("no replay"). The welcome envelope carries `lastEventId = eventLog.LatestID()`. If `since < earliestLive` OR `since > latest` the connection-level `onOutOfDate` (no SubscriptionID) fires immediately and `replayCursor` is set to -1 to disarm per-subscription replay. Otherwise each subscribe handler — `handleSubscribe` / `handleSubscribeObjectSet` / `handleSubscribeActionJob` — drops the `defer Unlock` pattern in favour of explicit locks so it can register the subscription, release locks, then drain `replayObjectSubscription` / `replayActionJobSubscription` onto `c.send`. Because the routing index is updated under the same hub.mu critical section as the snapshot read, there's no overlap between replayed events (id ≤ snapshot.maxID) and live events (id > snapshot.maxID). Pattern: when adding new event kinds that need replay support, give them a new `EventLogEntry.Kind` discriminator + a marshaller method on the entry, then thread them through the replay drain alongside the existing `objectChange` / `actionJobProgress` arms.

- For unit-weight centroids (every bucket smaller than `2c`), t-digest's `Quantile` is *linear interpolation between two consecutive sorted values at half-integer cumulative weights* — i.e., for `index = q·n`, `lower = ceil(index − 0.5)`, result = `(z2·v[lower-1] + z1·v[lower]) / (z1 + z2)` where `z1 = index − (lower − 0.5)`, `z2 = (lower + 0.5) − index`. The accounting matches the library's slice/struct layout: processed cap × 16 B + maxUnprocessed cap × 16 B + (len(processed)+1) × 8 B + struct overhead.
- `BenchmarkApproxPercentileTDigest_OneMillion` at b.N=1 measures the entire 1M-point ingest + Quantile cost, which makes per-op numbers dominated by allocator + sort time. If you need fine-grained Add-only timing, refactor to allocate the digest once outside the b.N loop and call `Add` inside; current bench keeps the e2e shape so the 78 ms/op is "what a real query would cost".

- The runtime injection half of US-371 was DONE in US-220 — `weave.callFunction(ref, params)` registered via `pkg/functions/goja_shim_functions.go::registerWeaveShim` with depth + cycle guards in `pkg/functions/fncall`. - Static cycle detection MUST use a "publish-time overlay" — the in-flight row's NEW source code overrides what the repo would return for the same identity. Without this an UpdateFunction that adds a cycle (B already calls A; you UPDATE A to call B) slips through because the repo still has the cycle-free A. Pattern: a small adapter struct that satisfies the lookup interface and short-circuits `(name, version)` / RID matches to the in-flight Function. Don't introduce parallel `nodes_json`/`edges_json`; the existing columns already serve. Only `fallback_model` + `max_retries` are genuinely new. This mirrors the US-370 lesson ("the existing functions table IS function_versions") — read the PRD as intent, not as a literal column list, and reuse what's there.
- Per-node retry config lives inside `node.config.retry = {maxAttempts, backoffMs}` so the schema didn't need extending. Validation is centralised in `validateRetryConfig(cfg)` and called from `validateNodeConfig` for every node type — i.e., retry config validation runs even on non-LLM nodes (tool / iterate / output) so a misconfiguration is caught before runtime regardless of where it sits.
- Iterate's body is dispatched via `runNode` (not `executeNodeWithPolicy`) on purpose: a partial iteration must not be retried wholesale, the per-body retry budget is honoured by `runNode` already (since runNode → runLLMNode/runToolNode is the same dispatch surface), and the flow-level fallback model semantics for nested LLM calls inside iterate are deliberately NOT applied (one well-tested fallback fire per node is the contract). The new `toInt(v)` helper accepts both `int` (from in-process callers / tests) and `float64` (from JSON unmarshal). When adding a future numeric knob inside Config, use the same helper rather than asserting `int` directly — JSON unmarshal will silently break direct int assertions.
- For flow-level MaxRetries the wire semantics are "additional retries beyond the first attempt" so total attempts = MaxRetries + 1. For per-node `config.retry.maxAttempts` the wire semantics are "total attempts" (so 1 = no retry). This is the Palantir convention; I picked it to keep the wire shape recognisable for SDK users coming from Foundry. Document at the SDK level if this distinction surfaces — internally `nodeMaxAttempts` always returns the "total attempts" form.
- `cloneStateForIterate` shallow-copies the parent state so iterations cannot leak per-iteration state into each other (or into post-iterate downstream nodes). The `iterate.<bodyId>` scope is scoped under the body node's id, so multiple iterate nodes in the same flow can coexist without their per-iteration item shadowing each other.
- The fallback policy fires AFTER all retries are exhausted, not interleaved. This matches "如果重试都失败再切" rather than "after each retry try the fallback". Production observability differs: `trace.Attempts` counts retries-on-primary; a fallback success bumps Attempts by 1 and stamps `UsedFallback=true`. SDKs can detect "primary exhausted but flow succeeded" by `trace.UsedFallback && status==success`.

**Learnings for future iterations:**
- `aip.Message` is the second AIP struct after `aip.Thread` to accept a nilable `*int64` JSON field. The Go JSON encoder renders `*int64=nil` as `omitempty` only when the field is tagged that way — without `omitempty` the wire shape would emit `"parentMessageId": null` and force every legacy SDK consumer to treat null as a meaningful state. Use `*int64` + `json:",omitempty"` whenever the field is genuinely tri-state (nil = no parent / set = parent id) instead of a sentinel int like 0 or -1.
- `ForkThread` MUST distinguish "pivot doesn't exist anywhere" from "pivot exists but in a different thread". A naïve implementation that builds a `byID` map only over `s.messages[srcThreadID]` collapses both cases to `ErrMessageNotFound`, which then surfaces as 404 to the SDK. The fix is a two-stage walk: sweep every thread's slice first to locate the pivot, then check `pivot.ThreadID == srcThreadID` separately. The HTTP layer already maps `ErrMessageNotFound → 404` and `ErrPivotThreadMismatch → 400`, so getting this right at the store keeps the contract crisp.
- The PG `ForkThread` recursive CTE was the trickiest piece. The naïve `WHERE id = c.parent_message_id` join doesn't compile in postgres because `c` doesn't see future iterations of itself; the working pattern is `JOIN aip_messages m ON m.id = (SELECT parent_message_id FROM aip_messages WHERE id = c.id)` — i.e., the recursive arm queries the parent column in a sub-select rather than projecting it through the CTE. `ORDER BY depth DESC` delivers the chain root-first so the re-insert loop can chain forward without a second walk.
- `MemoryStore.AppendMessage` now auto-links `ParentMessageID` to the last message on the same branch when the caller didn't pass one. This is critical for backwards compatibility with US-279 / US-284 callers that never set parent_message_id — without it every legacy linear thread would be a forest of disconnected roots in the new tree view. The PG store mirrors the same auto-link via a `SELECT id ... ORDER BY id DESC LIMIT 1`. Don't break this contract: future changes to the message schema should preserve the "no parent supplied → autolink to last" semantics so the tree view remains coherent.
- Fork's title default `"<src> (fork)"` is a UX lubricant, not an invariant — overrides via the `title` field in the request body win unconditionally. The provider is *not* overridable on fork by design (switching mid-branch would invalidate tool_call ids referenced earlier in the chain), but model and system prompt are because they're plain text the LLM treats per-turn. If a future US adds branch-id columns *to threads* (so a thread can carry multiple branches in-place rather than spawning new threads), revisit whether provider becomes per-branch — for now the "one provider per thread" invariant from US-279 is preserved.
- The `MessageTreeNode.Message *Message` pointer-embed is the right shape for SDK serialisers because it flattens the message fields onto the node JSON without a wrapper key. The alternative (named field `message: Message`) would force the SPA to write `node.message.id` everywhere — a worse UX. Document this in the SDK README when US-375 (UI tree browse) lands.
- AIP routes still don't need OpenAPI entries (per the US-373 / US-281 contract-test gate) because the contract test deps leave `AIPStore = nil`. If a future US wires a non-PG AIP store into the contract router, every AIP route will simultaneously need OpenAPI entries — plan for an "OpenAPI bulk add" PR at that point rather than incremental updates per US.

**Learnings for future iterations:**
- The PRD wording "pipeline_runs 表新增 last_committed_offset BIGINT" describes one column add but the full design needs THREE schema additions: the offset column on `pipeline_runs` (the per-run watermark), `pipelines.mode` (the runtime switch — 'APPEND' opts in, '' / 'FULL' keeps legacy semantics), and `pipelines.last_known_schema` (the persistent schema snapshot the diff compares against). Without the second schema-state column the schema diff has nothing to compare against on a fresh run and the BREAKING_CHANGE gate is dead code. Pattern: when a PRD describes a single column on a runs table for "incremental progress", check whether the *pipeline* row itself needs sibling state columns (config + cumulative state) — usually it does.
- `LatestCommittedOffset` MUST filter on `status='success'` — failed/canceled runs that were halfway through processing do NOT advance the watermark. A failed run at offset=200 with rows already partially written (some sinks are at-most-once, some at-least-once) cannot be "trusted" as committed; the next APPEND must re-read from the prior successful watermark to avoid silently dropping rows. Tests assert this with the `success/failed/success @ 100/200/150` shape — the result is 150 (max across successes), NOT 200 (max across all).
- The schema-evolution gate runs BEFORE any source read, on purpose. If the diff aborts mid-run (after rows have been ReadAfter'd), the source has already paid the read cost and may have advanced its own client-side cursor — wasted I/O AND a stale runtime state. By calling `Source.Schema(ctx)` first and resolving the diff against `pipelines.last_known_schema` before `Source.ReadAfter(ctx, ...)`, a BREAKING_CHANGE rejects the run cheaply. The `TestUS378_SchemaDiff_DroppedColumnReturnsBreakingChange` test asserts `src.readCount == 0` after the abort to lock this contract in.
- `MergeSchema` preserves the prior column order on purpose. Bleve facet positions, downstream Parquet schema ordering, and any client that consumes schema-positional offsets all benefit from a stable column ordering across runs. New columns append in observed order so a single-run schema rewrite is impossible — only ADD operations are allowed at evolution time, never REORDER.
- `typesEquivalent(a, b)` uses `strings.EqualFold(strings.TrimSpace(a), strings.TrimSpace(b))` because real-world schema sources mix `Long`/`long`/`LONG` and sometimes ship trailing whitespace from CSV-style sources. Case-sensitive equality would surface every cosmetic difference as a BREAKING_CHANGE conflict, blocking legitimate runs. The tightening is in *Name* matching (case-sensitive) — column names ARE case-sensitive in most downstream stores, while their type tags are not.
- The Defensive `filterAboveOffset(rows, cutoff)` re-filter in `RunIncremental` is intentional even though `IncrementalSource.ReadAfter` already promises "Offset > after" — connectors that filter client-side (e.g., a CSV connector that reads everything then filters) might leak rows below the watermark on a buggy implementation. The re-filter is a single pass over the slice; the cost is negligible compared to the safety gain.
- The `IncrementalSink` interface is intentionally optional (nil = preview mode). This unblocks two future US directions: (a) a "dry-run" pipeline preview UI that resolves the diff + reports the row delta without writing, (b) an "audit" run that captures the schema evolution history into a separate audit-only sink without touching the production index. Both can be built on `RunIncremental(ctx, opts)` without an interface change.
- `pkg/pipeline/incremental.go` is named at the package root (not under `pkg/pipeline/incremental/...`) because it's the new opt-in execution mode for the existing pipeline runner, not a separate service. The `Run*` API surface lives next to `RunDAG` so callers see both shapes when reading the package. If a future US adds CDC-style streaming, that's where a sibling `pkg/pipeline/streaming.go` would land — by mode, not by transport.
- The Store interface widening to add `LatestCommittedOffset` is backwards-compatible because all existing callers (handlers, scheduler) don't touch APPEND-mode state. New methods in interface go at the BOTTOM of the existing block grouped by US — easier to read the chronological evolution of the interface, and the `// US-298 — ... API.` / `// US-378 — ...` comments serve as section headers for future additions.

- US-379's "?asOf=tx-..." parameter shares the existing US-223

## 2026-05-03 - US-380 - WebSocket subscription cursor + replay

**Implementation:**
- `pkg/subscriptions/eventlog.go` (new): `EventLog` is a sliding-window
  FIFO of recently dispatched events keyed by a monotonic int64 cursor.
  `Append(entry)` returns the assigned cursor under a mutex so callers
  can stamp it on the outbound wire message in lockstep. `Snapshot(since)`
  returns the tail (entries with id > since) defensively copied for
  iteration without the lock. Eviction is `Window` OR `MaxEntries`
  (whichever fires first); defaults are 5 minutes / 10000 entries per
  the PRD. `EventLogEntry.Kind` discriminates `objectChange` vs
  `actionJobProgress`; aggregation events are NOT logged because they
  are per-subscription derived state and re-seed via Bleve at
  subscribe time. Marshal helpers on the entry produce the same JSON
  shapes that `HandleObjectChange` / `HandleActionJobProgress` would
  emit live, so replay drains never diverge from live dispatch.
- `pkg/subscriptions/hub.go`: `Message` envelope gains `Cursor int64`
  (per-event id, JSON `cursor`) and `LastEventID int64` (welcome
  high-water mark, JSON `lastEventId`). `HubConfig` gets an embedded
  `EventLogConfig`. `Hub` owns one `*EventLog` plus an exported
  `EventLog()` accessor for tests. `Connection.replayCursor` (int64)
  carries the parsed `?since=` value through to the subscribe
  handlers; `0` means no replay requested, `-1` is the post-out-of-window
  sentinel. `parseSinceCursor(raw)` is the URL parser — empty / negative /
  malformed all coerce to 0 so a bad client never fails the upgrade.
- `HandleWSWithUser` now reads `?since=<cursor>` BEFORE `websocket.Accept`,
  stamps the live high-water cursor on the welcome envelope, and emits
  a connection-level `onOutOfDate` (no SubscriptionID) if the requested
  cursor falls outside `[earliestLive, latest]`. The out-of-window
  branch zeros `replayCursor` (-1) so subsequent subscribes do not
  attempt per-subscription replay.
- `pkg/subscriptions/subscription.go::HandleObjectChange` and
  `pkg/subscriptions/job.go::HandleActionJobProgress` now `Append` to
  the log under `hub.mu` BEFORE reading the routing index, then stamp
  the assigned cursor on the outbound `objectChanged` /
  `actionJobProgress` messages. The single critical section guarantees
  the snapshot/index ordering invariant: subscriptions registered at
  hub.mu cannot miss events whose cursor ≤ snapshot.maxID, AND replay
  + live dispatch never deliver the same event twice (replayed cursors
  are bounded above by snapshot.maxID; live cursors are strictly above).

- The replay-and-routing-index invariant turns on doing the log
  `Append` and the `subIndex[objectType]` read in the SAME critical
  section. If the append moves out of the lock, a subscription that
  arrives between append and dispatch can both miss the live event
  AND replay it (because the replay snapshot would not include the
  un-stamped event). Pattern: any new event kind that needs replay
  must follow the same hub.mu append-then-route shape as the existing
  two paths. Don't optimise the lock window away.
- The subscribe handlers had to drop `defer Unlock()` in favour of
  explicit locks because the replay drain enqueues messages onto
  `c.send` and `c.send` is a buffered channel — under load (or in
  tests with a deliberately small buffer) the replay can briefly
  block on the writePump, and we must not be holding hub.mu during
  that wait. The aggregation subscribe handler had already adopted
  the explicit-lock pattern for the same reason; this story aligns
  the other three handlers with that convention.

  subscribe time. The reasoning: the client should know to refresh
  global state BEFORE re-establishing subscriptions, otherwise it
  will paint a partial view from `subscribed` → `objectChanged` and
  only later discover the gap. The connection-level `onOutOfDate`
  with empty SubscriptionID is the documented signal for "everything
  you knew is stale; do a full refresh and re-subscribe from scratch".

  negative / non-numeric / scientific-notation all coerce to 0 ("no

  natural extension of the rest of the websocket layer's policy
  ("don't let bad client input fail the connection") and matches
  how SSE Last-Event-ID handling already behaves elsewhere in the
  codebase. If a future story needs to surface "your cursor was
  malformed" to the client, add a fresh out-of-band notice rather
  than failing the upgrade.
- `EventLog.Snapshot(since)` returns `entries, minLive` so callers
  who care about the out-of-window verdict get both pieces atomically.
  At present `HandleWSWithUser` consults `EarliestID()` and
  `LatestID()` separately because the welcome path branches on each
  bound, but the unified accessor is there for future SDK helpers
  that want a single round-trip ("am I in the window?") API.
- Aggregation events not entering the log is a deliberate design
  choice: per-subscription derived state (running totals, group
  buckets) cannot replay correctly from a wire envelope; the only
  safe recovery is to re-seed via Bleve at subscribe time. If
  aggregation subscribers need replay-style continuity in the
  future, the right move is to carry a `lastSeenAggregationVersion`
  field on the subscription itself rather than logging the
  individual `aggregationChanged` payloads.
- Tests inject `EventLog.nowFunc` (private field) to simulate
  multi-second outages without sleeping. Pattern: keep the
  injection point package-private (not on `EventLogConfig`) so
  production code cannot accidentally drive it; tests in the same
  package retain access. Existing US-133/308 tests follow the same

  branch onto ctx is to actually call the helper with that
  non-default value. If a future US needs to know "did the caller

**Learnings for future iterations:**
- For "same key on different branches" semantics, the pattern is: (1) widen UNIQUE constraint to include `branch_id`, (2) default the column to `'main'` so legacy rows are still valid, (3) thread branch via context + `BranchScopeFromContext`, (4) lookups use `WHERE branch_id IN (current, 'main') ORDER BY (CASE WHEN branch_id=current THEN 0 ELSE 1 END) LIMIT 1` so the branch row wins when present, otherwise main is the fallback. This gives "branch overlay with main fallback" without per-method-signature plumbing — caller sets ctx once, every read in scope inherits.
- The function read path is more nuanced than ActionType because of semver: a branch can publish v2 while main has both v1 and v2. The Go-side `preferBranchFunctions(in, branch)` helper post-filters the SELECT result, suppressing main rows ONLY for `(name, version)` keys that the branch overlay covers. This way branches inherit unmodified versions of the trunk's history while shadowing the ones they republish. A branch publishing its own v2 does NOT hide main's v1 — that would be wrong, since the branch hasn't said anything about v1.
- Cache key composition: when adding branch awareness to a method that's wrapped by `CachedRepository`, the cache key MUST include `BranchScopeFromContext(ctx)`. The straightforward pattern is `BranchScopeFromContext(ctx) + "|" + existingKey`. Forgetting this means a warm-cache miss on the branch lookup returns the main row from an earlier unbranded request — silently wrong, no error, hard to debug. Done for `actionTypeAPI` and `actionTypeList` here; future methods that join the branch-aware club need the same treatment.
- The HTTP-handler shim `withBranchScope(r)` in `pkg/actions/handlers.go` returns a NEW `*http.Request` with the stamped context (rather than mutating `r.Context()` indirectly). This is the canonical Go way to propagate context through handler chains: every downstream `r.Context()` call sees the same stamped value without a separate `ctx` variable to forget about. The `oms.WithBranchScope` no-op for empty/main keeps the wrapper free of unnecessary allocations on the legacy path.
- The legacy `?branch=` overlay (admin handlers writing to `branch_changes`) and the new US-384 direct-row mechanism (writing to `action_types` / `functions` with `branch_id` stamped) coexist intentionally. The overlay is the "branch as patch" model used by interactive PR-style flows (BranchedRepository decorator); US-384 is the "branch as named version" model used by the action/function dispatch path. A future US can converge them if needed; for now they target different surfaces and both are valid.
- The `ON DELETE` policy on `action_types.branch_id` is intentionally absent — there's no FK to `ontology_branches(id)` because the branch column is also used as a free-form namespace (any string the system's branch-scope context wants to use). If a future US needs FK enforcement, add it as a separate constraint that drops gracefully when the branch is removed (`ON DELETE CASCADE` would silently drop a branch's published actions, which is probably the wrong policy for an audit-trail system; `ON DELETE SET DEFAULT 'main'` would silently merge the rows into trunk, also wrong). Leave the column free-form unless a clear policy is decided.
- `DISTINCT ON (api_name)` requires the leading column of the `ORDER BY` to match the DISTINCT ON column. Then secondary ordering picks the winner for each distinct group. This is the cleanest SQL way to express "give me the branch row if present, else main, one row per apiName" without a window function or a self-join.
- Branch direct-merge with explicit conflict resolution (US-385): `pkg/oms/handlers_branch_merge.go` adds two new endpoints — `POST /branches/{branchId}/diff` returning the categorised AnnotatedDiffEntry buckets (added/modified/deleted) plus an inline AnnotatedMergeConflict list, and `POST /branches/{branchId}/merge` that consumes `conflictResolution: { "<entityType>:<apiName>": "use-branch"|"use-main" }` and applies the branch changes accordingly. The conflict detector reuses `detectConflicts` from `handlers_proposal.go` so the rebase / proposal / direct-merge paths share one source of truth. The conflictResolution key shape is "<entityType>:<apiName>" (entityType is already lowercase by storage convention — objectType / actionType / linkType / property — so no case-folding is applied to keep the key strictly equal to what the diff endpoint emits). apiName is sourced from `apiNameFromState`, which probes a `{ apiName string }` shape against the JSON payload (works for ObjectType / Property / LinkType / ActionType because they all expose `apiName` at the top level of their wire shape). For DELETED changes apiName is read from `BeforeState`; for ADDED/MODIFIED from `AfterState` with `BeforeState` as a fallback. The merge handler scans every conflict against the resolution map BEFORE writing any rows: if any conflict lacks a resolution it returns 409 MERGE_CONFLICT with both `conflicts` (full annotated list) and `unresolved` (the subset missing a key); the branch stays open and main stays untouched. When every conflict is resolved, "use-branch" entries flow through `applyAdd/applyModify/applyDelete` exactly like the proposal merge path, and "use-main" entries are skipped — `appliedCount` / `skippedCount` in the response let the caller verify the split. `IncrementOntologyVersion` only fires when at least one change was actually applied (a "skip everything" merge still flips the branch to merged but doesn't bump main's version, since nothing changed). Pattern: when adding a new conflict-aware mutation surface, derive the conflict identity from the entity payload (apiName) rather than the random EntityRID — apiName is human-readable and survives serialisation round-trips, while EntityRID can be rebuilt by replays / packaging tools and would force the UI to show opaque RIDs in the resolution UX.

- Per-ontology branch state (rather than a single global "active branch") matches the backend's per-ontology `ontology_branches` table. **Learnings for future iterations:**
- The merge endpoint's 409 body is the project's first non-`ApiError`-shaped error response. The standard `request()` helper would discard the `conflicts` / `unresolved` arrays because it parses errors into `ApiRequestError` (which only carries `errorCode` / `errorName` / `parameters`). Solution: bypass `request()` for the merge call and read the JSON body directly, branching on `status === 409 && parsed.errorCode === 'MERGE_CONFLICT'` to throw a typed `MergeBranchConflictError` carrying the structured payload. Other failures still flow through `ApiRequestError` so call sites that don't care about the conflict shape behave identically. Pattern: when an endpoint returns a structured error envelope that doesn't match the standard `ApiError` shape, define a typed `Error` subclass per endpoint and short-circuit the response parsing for it; don't try to widen `ApiRequestError` because that would force every consumer to handle the new fields.
- React-i18next `t()` returns the raw key (e.g. `"branchReconcile.merging"`) when the i18n instance is not initialised in tests. The existing test setup (`web/src/test/setup.ts`) does NOT bootstrap i18n, so RTL tests must NOT assert on translated strings — assert on `data-testid` markers, props (`disabled`), or the dynamic data values that flow through the component (e.g. branch ids, `apiName` strings). The BranchPicker test follows the same convention and is the canonical reference. If a story genuinely needs translated copy under test, set up an `i18next.init({lng:'en', resources})` in a per-test wrapper rather than mutating the shared setup file.
- For test data attributes that include colons (e.g. `data-testid="reconcile-conflict-${resolutionKey}"` where the key is `actionType:updateOrder`), `screen.getByTestId('reconcile-conflict-actionType:updateOrder')` works directly — RTL's testid lookup uses string equality, not CSS selector parsing, so colons are not interpreted. This is the right shape because `resolutionKey` is the conflict's stable identity (`<entityType>:<apiName>`) and matching it 1:1 in the testid lets E2E tests select an exact conflict row without index gymnastics.
- The reconcile page deliberately re-renders the conflict list using `serverConflicts` (set from the 409 body) rather than re-fetching the diff. This is faster (no extra round trip), keeps the user's existing radio selections intact for the still-conflicting subset, and matches the backend's behaviour of computing conflicts on every merge call (so a re-fetch of `postBranchDiff` would return the same list anyway). The `useMergeBranch` mutation also invalidates the `branchDiffPost` query key on the *successful* path so a navigation-back later reflects the merged state.
- The `mergeBranch` helper in `ontologies.ts` re-exports the static `withActiveBranch` and `ApiRequestError` from `./client` rather than dynamic-importing them. Dynamic imports inside an async handler work but make TypeScript inference and test mocking harder. Static imports at the top of `ontologies.ts` are the canonical pattern and match what every other API helper in this file does.
- Backend `MergeBranch` rejects branches with `status != "open"` (409 BranchNotOpen) BEFORE inspecting the body, so a closed-branch user hitting "Merge" surfaces as an `ApiRequestError` with `errorCode: "BranchNotOpen"`. The page also pre-disables the merge button when `branch.status !== 'open'` so the user gets immediate visual feedback instead of relying on the round-trip 409. Keep both guards: client-side disable for UX, server-side reject for correctness.
- The "Open Reconcile UI" link from `BranchDiffPage` is the discoverability bridge — without it users would have no way to find the new surface unless they typed the URL. Adding the link in the header (rather than the body) keeps it visible regardless of how many diff entries the page renders. When introducing a new sibling page that supersedes an existing read-only surface, mirror this pattern: keep the legacy page operational, add a link from its header to the new page, and note both in the route table.

**Learnings for future iterations:**
- The acceptance criterion has THREE parts that look like one feature: (a) `dataset_transactions` table with `parent_tx_id` (already built in US-379, migration 000090), (b) `POST /transactions` for explicit checkpoints, (c) `POST /rollback?to=tx-...` for the actual time-travel effect. The first part is reused as-is; the second is an empty-edits checkpoint stamper; the third is the surgical part. Don't conflate them — the rollback is the only one that touches user-visible state, the checkpoint is metadata-only.
- The rollback's "write isolation" semantics (PRD: "写入按 tx 隔离") translate to: every `POST /rollback` records a fresh bookkeeping tx whose `parent_tx_id = target.TxID`, NOT the prior chain head. This intentionally branches the chain visually — a future `?asOf=tx-...` read past the rollback resolves correctly because the rollback's CommittedAt > target's CommittedAt and `committed_at`-ordered scans still find the right snapshot. The audit overlay (`rolled_back_at` / `rolled_back_to_tx_id` on the abandoned txs) lets a future history view render the "deleted" branch with strikethrough rather than dropping it.
- Self-pointer convention: the bookkeeping row sets `rolled_back_to_tx_id = target.TxID` (NOT its own TxID). This makes the audit semantics clean — every row with a non-NULL `rolled_back_to_tx_id` either (a) was rolled back (its own state is stale, points at the rollback target), or (b) IS a rollback bookkeeping row (its state is canonical, points at the rollback target). The schema doesn't disambiguate the two cases — the join with `parent_tx_id` makes (b) detectable (rollback rows have parent = the same target).
- Replay degrades, marks don't. The handler returns 200 even with nil affected/history/index — the chain audit overlay always flips, but `RestoredObjects` / `DeletedObjects` stay 0. This matches the PRD's "rollback is a metadata-first operation" semantics: a system without a replay infrastructure (e.g. a fresh Bleve cluster being rebuilt) should still be able to flip the chain. Conversely, a `MarkRolledBack` failure DOES abort the handler — a half-marked chain is genuinely incoherent and would surface as a stale `?asOf=tx-...` read returning the rolled-back state.
- The replay walks `affectedStore` keys, NOT `ListAfterCommittedAt`'s tx list. The two views differ on purpose: the tx list is the AUDIT axis ("which txs to mark"); the affected-keys list is the OBJECT axis ("which docs to replay"). A single tx can touch hundreds of PKs; conversely a long sequence of compensating edits can re-touch the same PK across N txs but the replay only needs the latest snapshot at target's CommittedAt — one re-index per affected (objectType, pk) is sufficient.
- Bucketing affected keys by `ObjectTypeRID` BEFORE iterating cuts the snapshot fetches from O(affected_keys) to O(distinct_object_types). For a typical rollback that touches N rows of M ObjectTypes (N >> M), this is the difference between minutes of round-trips and milliseconds. Done by `byOT := make(map[string][]string)` in `replayObjects`.
- `crypto/rand` for the tx id (16 bytes = 128 bits) is overkill for a single-machine deployment but matches the rest of the project's RID minting and avoids the time-precision ambiguity of `tx-20260503T...`. The fallback to a time-based id when `crypto/rand` errors is a defensive hedge that keeps the handler making forward progress on platforms where `getrandom(2)` is mis-configured.
- The `datasetTransactionWriter` interface composes `datasetTransactionLister` rather than re-declaring the read methods. This means a future story that adds a new read method to the lister (e.g. `ListByUser` for an audit drill-down) automatically picks it up in the writer surface and no per-method ceremony is needed in the rollback handler. Same composition pattern as `oms.DatasetTransactionStore` extending a hypothetical reader interface.
- `nilIfEmpty(rolledBackToTxID)` in the `MarkRolledBack` UPDATE is the canonical PG nullability shim: empty Go string → SQL NULL, non-empty string → TEXT value. Used throughout the repo for `parent_tx_id` / `user_id` / etc. — keep using it for any new nullable column to avoid the "stored empty string vs NULL" ambiguity that breaks `WHERE col IS NULL` queries.
- The cmd/server `historySnapshotStore` interface (in `history_snapshot_provider.go`) and the new `datasetRollbackSnapshot` interface (in `dataset_rollback_handler.go`) have IDENTICAL method shapes — both expect `SnapshotObjectsAt(ctx, objectTypeRID, asOf) ([]oms.LatestObjectState, error)`. **Learnings for future iterations:**
- US-384 already shipped the persistence + read-side branch dispatch for Functions (column, UNIQUE constraint widening, `BranchScopeFromContext`-aware repo methods, ExecuteFunction stamping `?branch=` onto the request context). US-389 closed the publish-side gap: until this story, the `BranchID` field on the wire model was effectively read-only because `CreateFunction` never populated it from the request, so every newly-published row landed on main regardless. The fix was small-scoped — request struct + handler resolution + cycle ctx + 409 envelope — exactly because the storage/read story was already done. Pattern: when a feature splits into "branch-aware reads" and "branch-aware writes" stories, expect the writes story to be the much smaller one if reads landed first.
- The `?branch=` query vs `branchId` body precedence rule is "query wins" because the read path uses query exclusively (`r.URL.Query().Get("branch")` → `WithBranchScope`). Honouring both inputs with query taking precedence keeps the wire shape symmetric across publish and read while still letting SDK builders that can't easily mutate the URL pass the branch in the body. Don't surface this ambiguity as a 400 — that would break SDKs that do both for belt-and-braces and is a footgun for no real benefit.
- `WithBranchScope(r.Context(), branchID)` MUST wrap the cycle-detection call site even though the ctx is not threaded into the persistence call below it. Reason: `detectFunctionCallCycle` walks the call graph through `repo.GetFunctionByName` and `GetFunctionByNameVersion`, both of which read `BranchScopeFromContext(ctx)`. Without the wrap, a branch publish whose new code calls `weave.callFunction("helper")` would resolve `helper` against main instead of the branch's overlay, and a cycle that exists on the branch overlay (A→B → branch publish B' → B→A) could slip through validation. The persistence call below it doesn't need the same ctx because the row's own `BranchID` field is the source of truth at INSERT time — but the cycle scan reads OTHER rows from the repo and those reads need the scope.
- The 409 envelope `parameters.branchId` is the canonical disambiguator for "which branch did the duplicate hit" — with US-384's widened UNIQUE shape, the same name@version pair can legitimately exist on N branches and the bare `name`+`version` from the legacy envelope is no longer enough to identify the conflict. Pattern: any error response whose root cause depends on a column that branch-overlays widened MUST surface that column in `parameters` so SDKs/UIs can render unambiguous messages.
- Test mockRepo branch-awareness pattern: when the production read path consults `BranchScopeFromContext(ctx)` AND filters with a SQL `WHERE branch_id IN (current, 'main')` AND post-filters with `preferBranch*`, the in-memory mock must reproduce ALL THREE behaviours to give handler tests fidelity. The `mockPreferBranchFunctions` helper in `pkg/oms/mock_functions_test.go` mirrors `pkg/oms/pg_repository.go::preferBranchFunctions` with identical semantics — when adding new branch-aware repo read methods, expect to add the corresponding mock helper too. Without this, handler tests would silently miss branch-specific routing bugs (the in-memory mock would always return both main and branch rows, masking the production "branch row wins" predicate).
- The legacy `CreateFunction` test in `handlers_function_test.go::TestCreateFunction` continues to pass unchanged after the request struct widening because `BranchID` is `omitempty` on the wire and the resolution path normalises the empty string to `DefaultBranch`. New optional fields on existing publish APIs should always default-normalise so legacy callers don't need a code change.
- The repository's `UpdateFunction` was deliberately NOT widened to honour a branch override on the body. The branch is set at create time and immutable thereafter — to "modify a function on a branch" the user creates a NEW row with the same `(name, version)` on the target branch (the standard publish flow). **Learnings for future iterations:**
- The PRD wire shape `{type:'row', children:[{type:'col', width:6, child:{type:'component'...}}]}` constrains the validator strongly: row's direct children MUST be cols (never plain components, never nested rows), cols MUST have a width AND a child, components are leaves with a componentType identifier. The validator codifies this exactly so a future SPA editor that accidentally produces malformed JSON gets a clear `path` into the offending node rather than a generic "invalid layout" error. Pattern: when the PRD includes a wire example, test EVERY constraint that example implies (positional, width range, sum-bound, type-tag enum) — the example is the contract, not just a hint.
- `json.Decoder.UseNumber()` is the canonical way to distinguish integer 6 from float 6.5 in a generic `map[string]any` decode. Without it, both arrive as `float64(6)` and `float64(6.5)` and the integer check needs a `math.Trunc(v) == v` workaround. UseNumber gives you `json.Number` directly and `Int64()` errors on a non-integer literal — that's the test for "this is a valid grid width". Keep this pattern for any future DSL field that requires strict-integer semantics.
- The version-bump contract is "every Update is auditable history, including no-op updates". This trades a slight churn cost for a clean audit invariant: `app_versions` row count = number of `PUT /apps/{rid}` calls that succeeded with owner-gated 200. A "skip empty updates" optimization would corrupt this invariant and break the future US-398 rollback UI's per-action timeline. Don't add empty-update suppression without re-considering the audit contract.
- `SELECT … FOR UPDATE` on the live `apps` row inside the Update transaction is the cheapest way to make concurrent updates race-free. Without it, two simultaneous PUTs would race the version bump and either (a) leak two `app_versions` rows at the same version (PRIMARY KEY violation, transaction rollback) or (b) overwrite each other's layout with the version reading stale. The lock is held only for the duration of the UPDATE + INSERT pair; release happens at COMMIT. Pattern: any feature whose model has a "monotonic version + history append" shape needs FOR UPDATE on the live row inside the transaction.
- Degraded-mode (nil store) routing: every endpoint returns 500 `AppsUnavailable` rather than 404 because the routes ARE mounted but the backing infrastructure is missing — this lets the SPA's API client distinguish "feature disabled on this deployment" (500 with named errorCode) from "bad URL" (404). The dashboards / saved-searches / action-templates packages all share this shape; reuse it for any new feature that's gated behind a PG-only store.
- The `apps` routes are NOT in `api/openapi.yaml` because the contract test router leaves `deps.AppsStore = nil`, gating the mount block. **Learnings for future iterations:**
- The PRD AC names "useObjectSet hook" but a top-level `useObjectSet` already implicitly exists in the codebase as `useLoadObjectSet` (TanStack Query wrapper) plus a richer ObjectSetResults pagination state machine. For the App-Editor binding we want a *combined* hook that owns the cursor stack + sortOverride + variable substitution, so the right move was to layer `useAppObjectSet` on top rather than rename either one or duplicate the fetch logic. Pattern: when an AC asks for a "use X hook" and the codebase already has a query-side primitive, build the page-level hook ON TOP and keep the query-side primitive lean — don't merge them.
- React's "previous prop reset" pattern (`useState(initial)` + `if (prev !== current) { setPrev(current); setOther(...) }`) is the lint-clean way to reset derived state synchronously when an upstream prop / memo key changes. `useEffect` is one render too late: between the new prop arriving and the effect firing, an event handler could touch the stale state and mint a request that the server rejects. The cursor-token-on-stale-definition footgun in `useAppObjectSet` is exactly that shape — `react-hooks/set-state-in-effect` forbids the easy fix, `react-hooks/refs` forbids the ref tracking workaround, so the React docs' state-during-render pattern is the only path that clears all three constraints.
- ObjectSet RID detection: any string starting with `ri.objectSet.` or `ri.object-set.` (the project's two attested ObjectSet RID prefixes) routes to `{type:'reference', reference}`; anything else routes to `{type:'base', objectType}`. Don't add a third prefix detection layer for legacy RID variants — surface failures as 404 from the server instead. The two-prefix split is small enough to inline; growing it past two should be promoted to a shared util in `web/src/lib/`.
- Table column headers as a sort-toggle UX pattern: store `sortOverride` as `{field, direction} | null` (NOT `field+'-asc'` strings) so a future multi-column sort (shift-click) extends the same state shape with no schema change. Toggling the same column flips direction; clicking a different column resets to asc; null falls back to the author's default. The default-vs-override split lets authors set up a sensible initial render without disabling user interaction — same pattern used by the Browser page's column headers.
- Variable substitution must happen BEFORE the JSON definition is hashed for the cache key, otherwise TanStack Query treats `{{country}}` and `'JP'` as the same definition and never refetches when the variable flips. The cache-key principle: any string inside the wire payload that the client resolved from app state should reach the cache key in its resolved form.
- `useAppObjectSet` returns `{loading: query.isLoading || query.isFetching, ...}` so the `data-table-state` attribute flips to `loading` on background refetches too. Without the OR, a refetch triggered by sort change would render with the prior data + `loading=false`, masking the in-flight fetch from CSS / E2E selectors. Pattern: when surfacing loading state to the UI, treat `isLoading` AND `isFetching` as the same "in-flight" signal unless the caller explicitly needs the cold-vs-warm distinction.
- The test setup needs both the `ontologyStore` selector-aware mock (carried over from US-394) AND a real `QueryClientProvider` wrapper around `<AppEditorPage />` because `RuntimeTable` calls `useQuery`. The hook-level tests use the standard `renderHook(..., {wrapper: makeWrapper()})` recipe; full-page tests need a second wrapper. Don't try to mock `useLoadObjectSet` itself — the QueryClient stub is cheaper, less brittle, and exercises the real query-key memoisation path.
- The runtime Table tests use `getAllByTestId('app-runtime-table-cell-name')[idx]` for cell assertions because every row produces a cell with the same `data-testid`. If a future iteration adds row-id scoped testids (e.g. `app-runtime-table-cell-name-{primaryKey}`) prefer that over per-row index lookups — index lookups break under sort / pagination changes in tests.

## 2026-05-04 - US-396 - App 发布与共享

**Implementation:**
- Migration `000095_apps_publish.{up,down}.sql` adds three nullable columns to `apps`: `published_version INT`, `published_at TIMESTAMPTZ`, `published_by TEXT`. Two CHECK constraints enforce (a) `published_version >= 1` and (b) the all-or-nothing consistency invariant — the three columns are stamped + cleared atomically so an App can never carry a partial publish state.
- `pkg/apps/model.go::App` gains three pointer fields with `omitempty` JSON tags so never-published Apps still serialise without `null` noise (validated by `TestAppJSON_OmitsPublishFieldsWhenUnset`).
- `pkg/apps/store.go`: new `PublishedAppView` wire type (parent identity + pinned version + snapshot LayoutJSON, served read-only). `Store` interface gains three methods: `Publish` (owner-only, returns the freshly-stamped view), `Unpublish` (owner-only, idempotent — but ErrNotFound if RID absent or owner mismatch), `GetPublished` (NO owner gate — any authenticated viewer; distinguishes `ErrNotFound` from new sentinel `ErrNotPublished`).
- `MemoryStore` implementations of all three; `cloneApp` extended to deep-copy the new pointer fields.
- `pkg/apps/handlers.go`: three new chi routes — `POST /api/v2/apps/{rid}/publish`, `POST /api/v2/apps/{rid}/unpublish`, `GET /api/v2/apps/{rid}/view`. Publish + Unpublish reuse the owner-context pattern; View only requires `requireAuth` (no owner gate). `writeStoreError` gets a new arm mapping `ErrNotPublished` → `404 AppNotPublished` so viewers see a distinct envelope from "RID does not exist".
- `cmd/server/apps_store.go`: pgAppsStore `getRaw`/`List` SELECTs widened to include the new columns; new `Publish` method runs a `SELECT ... FOR UPDATE` + `UPDATE apps` + same-tx snapshot read so the published view returned by the call reflects exactly what landed. `Unpublish` is a single owner-gated UPDATE that returns ErrNotFound on zero rows. `GetPublished` is a two-query read (live row → app_versions snapshot) with the published_version nil-check between them.
- `web/src/api/apps.ts`: `App` interface gains optional `publishedVersion` / `publishedAt` / `publishedBy`; new `PublishedAppView` interface and `publishApp` / `unpublishApp` / `viewApp` helpers — keeps the TS surface in sync with the Go model so future SPA work doesn't have to re-derive the types.

**Learnings for future iterations:**
- The acceptance criterion says "POST /apps/{rid}/publish 创建只读 version", but the existing `app_versions` table already records every Update as an immutable snapshot, so US-396 doesn't need a new snapshot table — we just pin which existing version is "the published one" via three new columns on `apps`. Re-publishing simply advances the pin to the current `apps.version`. This keeps the schema flat and the TTL-policy story trivial (publish state lives or dies with the App row).
- The viewer surface is the FIRST `pkg/apps` endpoint that breaks the owner-private gate. The split is `requireAuth` (any user) vs `requireAuth + owner check` (owner-only). When future stories add other "shared with org" surfaces (read-only dashboards, comment threads), follow the same pattern: a NEW handler that drops the owner gate AND a new sentinel that distinguishes "RID exists but viewer can't see anything" (ErrNotPublished/AppNotPublished) from "RID does not exist" (ErrNotFound/AppNotFound). Collapsing both to 404 NotFound is tempting but loses information the SPA needs to render different empty-state UIs.
- The CHECK constraint pattern `(all NULL) OR (all NON-NULL)` is the right way to encode publish-state atomicity at the DB level — it prevents a half-applied UPDATE from leaving rows in a "published but no audit metadata" state. Use the same pattern when adding any new multi-column status block (e.g. `archived_at + archived_by`, `locked_at + lock_holder`).
- Keep TS bindings in sync with Go DTOs in the same commit, even if no SPA story asks for it yet (US-396 has no "Verify in browser" criterion). The cost is low (one short export) and the alternative — a future story re-deriving `PublishedAppView` from scratch — repeatedly burns review cycles on shape mismatches.
- Pattern: when extending an existing Store interface, BOTH the MemoryStore AND the cmd/server PG store must implement the new methods, plus `cloneApp` (or equivalent deep-copy helper) must be widened for any new pointer/slice fields. Forgetting `cloneApp` is silent — tests that pass the original pointer may stay green while concurrent callers see torn writes.
