  - OpenAPI ↔ chi contract test lives at cmd/server/contract_test.go:TestContract_AllRoutesDocumented — it fails with a precise list of undocumented routes.   - ActionType "rules" and the admin builder's internal state diverge: the wire shape is typed in ontologies.ts as `ActionTypeRule` (discriminated by `type` + optional type-specific fields), but the UI keeps friendlier shape `BuilderRule` with `bindings: BuilderRuleBinding[]` (array, for stable ordering/editing) — `builderRulesToWire` converts the array back to the backend's `propertyBindings: Record<propName, {type, value}>` shape on submit

A future iteration can parse `"true"` / `"42"` into proper JS types, but server-side type coercion via ValueType constraints (US-111) already handles this for most cases; keep the UI dumb
  - For pages with multiple CRUD modals, always give the page-edit-table buttons AND the modal-confirm button distinct aria-labels, OR scope the modal query via `heading.closest('div[class*="rounded-xl"]')` + `within(modal).…`. The Delete button text collision cost me one red test run — fix documented as Testing gotcha #6
  - TypeScript vs. deep-clone test fixtures: `JSON.parse(JSON.stringify(ACTION_TYPES))` returns `any` to TS. To keep the test type-safe, declare a looser `StoredActionType` interface for the mock state and annotate the `created` object literal against it — TS won't complain about the `any` clone once the state field is typed

- **Learnings for future iterations:**
  - The PRD AC pointed at `GET /api/v2/ontologies/{ontology}/audit` — that route does NOT exist in api/openapi.yaml nor routes.go. The only audit read endpoint is `GET /api/v2/admin/auditEvents` (global, admin-only, gated by `auth.PermUserManage`). Audit events carry a `resource_rid` but there is no ontology filter on the endpoint; if a future story demands per-ontology scoping, add a `?ontology=` filter to `audit.ListFilter` / `PGStore.List` rather than a brand-new route
  - TanStack Query v5 `useInfiniteQuery` requires `initialPageParam` (v4 didn't) — use `''` for "start, no cursor", coerce to `undefined` in the fetcher so the `pageToken` query param is only appended on subsequent pages. `getNextPageParam: last => last.nextPageToken || undefined` is the standard shape for opaque-token servers
  - Entity-type dropdown populating: for audit specifically, the set of resource types is FIXED (backend only records a small enum: ObjectType, Property, LinkType, ActionType, Interface, SharedProperty, ValueType, TypeGroup, Function, QueryType, Session). Hard-coding the list in `ENTITY_TYPES` is acceptable — a dynamic "derive options from first page" approach would skew the dropdown based on what happened to have been recorded recently
  - `diff_json` shape is not fixed — sometimes `{before, after}`, sometimes a flat map, sometimes null. `DiffView` sniffs for `{before, after}` shape first (renders side-by-side), falls back to a raw `<pre>` JSON dump otherwise. Check `diff !== null` BEFORE `Object.keys(diff).length === 0` to avoid "No diff" showing for truthy objects
  - Testing gotcha #8: when a resource type (e.g. "ObjectType") is ALSO a dropdown option for the Entity-type filter, `getByText('ObjectType')` throws with multiple matches. Prefer `getAllByText(...).length >= 1` or target a row-scoped container (e.g. `getByLabelText('Audit event evt-create')`). Same shape as prior gotchas but new because the filter options overlap the data labels
  - `user.type(input, 'alice')` on a filter input triggers ONE refetch per character via useInfiniteQuery — the assertion `filtered.length >= 1` is the safe expectation, not a strict call count. Tests that want exact call counts should debounce the filter at the hook layer (not yet needed)
  - `datetime-local` inputs emit `YYYY-MM-DDTHH:mm` — convert via `new Date(str).toISOString()` before sending as RFC3339 `since`/`until` query params. No library needed; the browser handles TZ math
  - When removing the last placeholder from `AdminPlaceholderPage.tsx`, ALSO delete the placeholder test file — the generic `AdminPlaceholderPage` component is no longer referenced by any App.tsx route and exists only for potential future placeholders
