If a future PRD asks specifically for H3 resolution semantics and CGO is acceptable for that deployment, the Dockerfile will need `apk add gcc musl-dev` + `CGO_ENABLED=1` — a deliberate choice, not a default.
- New GroupBy type extension (geohash, future grid-like groupers): (1) add dispatch case in `Engine.getGroupEntries`, (2) new `getXxxEntries` that walks Bleve hits once with `Size=e.MaxDocScanSize`, buckets doc IDs by key, and returns a `groupEntry{value, scopeQuery=DocIDQuery}` per bucket — same shape as `getDurationEntries`, (3) declare the groupBy-specific tuning knobs as pointer fields on `GroupBySpec` (e.g. `Precision *int`) so absent=default is distinguishable from zero, (4) extend OpenAPI enum + schema props + embedded copy. Bleve's MaxDocScanSize naturally bubbles APPROXIMATE accuracy — no custom truncation plumbing. The derived-aggregation path in `handler_aggregate_derived.go` only supports `exact` groupBy, so new types silently reject there — that's fine.
- Bleve geopoint field retrieval shape: searchReq with `Fields=["..."]` returns the geopoint as `[]float64{lon, lat}` — note the ORDER (lon first, lat second) and the concrete `[]float64` type (NOT `[]interface{}`). Decoder helpers must handle `[]float64` as a primary case; `[]interface{}` + `map[string]interface{}` are fallback shapes for non-Bleve-fed callers. See `pkg/oss/aggregation/geohash.go::decodeGeopoint` for the canonical shape-tolerant decoder — accepts lat/lng/lon/latitude/longitude key variants.
- Cube/Rollup are "meta-groupBys" that expand into N subsets then reuse `recursiveGroupBy` per subset. Hook the expansion BEFORE the recursion (branch at `AggregateWithQuery` dispatch), never inside `recursiveGroupBy` — that way null-bucket handling, ordering, truncation propagation, and sub-aggregation attachment all just work. Non-grouped dimensions on a cube/rollup row are ABSENT from `row.Group` (key absence = aggregated, matches SQL GROUPING() semantics). Export the combination generator (`aggregation.ExpandGroupByCombinations(n, cube, rollup)`) so the derived-field aggregation path in `pkg/oss/objectset` can reuse it without duplication. Cube on N dims = O(2^N) — document the fan-out, consider a hard cap if a future story sees N>8.
- `bleve.NewFuzzyQuery` vs `MatchQuery.SetFuzziness`: distinct primitives with distinct inputs. MatchQuery runs the text analyser on the value (lowercase, tokenise) then applies per-term fuzziness; FuzzyQuery treats the value as a single PRE-ANALYSED term and does one Levenshtein lookup. For single-token matches ("Kafka matches Kafca") FuzzyQuery is the right primitive — cheaper, sharper, no tokenisation surprises. For multi-word user input (containsAnyTerm "hello worlld") MatchQuery.SetFuzziness is correct. The `where.fuzzy` operator added in US-232 lowercases the input (`strings.ToLower`) before handing it to FuzzyQuery so it matches the default analyser's indexed form — skipping that step silently returns zero hits on any mixed-case query.
- Query-string overrides for request-body fields: the search `?fuzziness=N` override pattern is worth repeating. Parse the query param; if it's a valid integer within range REPLACE `body.Fuzzy` entirely (explicit 0 means "disable, set to nil"); if parse fails OR out of range return a typed 400 (`InvalidFuzziness`). If the query param is absent, still validate `body.Fuzzy.MaxEdits` for the same bounds — otherwise callers can bypass validation by sending a junk body. Single source of truth for the upper bound: `where.MaxFuzziness`.
- Bleve (v2.5.7) phrase-with-slop requires a CUSTOM `query.Query` + wrapping searcher. Bleve hardcodes slop=0 at every `NewPhraseSearcher` / `NewMultiPhraseSearcher` call site — `findPhrasePaths` accepts `remainingSlop` internally but it's always 0 from the public API. Pattern: build `ConjunctionSearcher` of per-term `TermSearcher`s (every phrase term must be present) then wrap with a searcher whose `Next()` calls `dm.Complete(scratch)` and validates the position map against a Lucene-style slop budget (`|expected - actual|` summed across adjacent terms ≤ slop, where `expected = prevPos + 1`). MUST set `options.IncludeTermVectors = true` INSIDE the Searcher builder before constructing TermSearchers — options are captured at construction, not runtime. Slop=0 + multi-term should still delegate to `bleve.NewMatchPhraseQuery` (optimised path, identical semantics); the custom searcher only engages when slop > 0. Single-term phrases collapse to a plain `TermSearcher` (no conjunction wrap). Add `q.(*ExpectedType)` assertion tests as cheap insurance against a future contributor "simplifying" away the optimised path. See `pkg/oss/where/phrase_slop_query.go` — US-233.
- Lucene-style phrase-slop syntax (`"quick fox"~2`): only treat the LAST `~<digits>` suffix as slop (`strings.LastIndex + all-digit-tail check`), so phrases legitimately containing `~` survive the round-trip (regression test: `"foo~bar"~1` parses as phrase=`foo~bar`, slop=1). First iteration that used `strings.Split("~")` broke on this. Accept an unquoted bare string as a phrase with slop=0 so callers can always use the operator symmetrically, and accept both `'...'`/`"..."` as the quote delimiter.

The pattern handles withProperties/derivedProperties/where uniformly without the detector growing per-type cases.
  - The "required relaxed is not breaking" semantic is easy to get wrong on first pass — it's tempting to treat ANY isNullable flip as breaking. Always implement breaking-change detectors as DIRECTIONAL: `was X, now Y` matters in only one direction. Add a positive-and-negative test pair (REQUIRED_ADDED breaking + nullable-relaxation no-op) to lock the direction.

- **Learnings for future iterations:**
  - In-band error reporting is the only viable pattern for NDJSON streams. By the time the executor fails, the server has already written `200 OK` headers — flipping to a 4xx/5xx response is impossible. Reserve the JSON status-code path for pre-execution gates (validation, 404, quota, no-executor); all post-execution failures must surface as a terminal `{"error": ...}` line. SDKs MUST handle both: try/except around the generator-returning call to catch HTTP errors, AND try/except inside the loop to catch in-band errors. Document this dual contract explicitly — it's the most common SDK consumer mistake.
  - `enc := json.NewEncoder(w)` writes a trailing newline by default — this is what makes the output NDJSON-compliant. Do NOT manually append `\n` after `json.Marshal`; you'd double-newline and break some strict parsers. Pair every `enc.Encode(...)` with a `flusher.Flush()` call in the same line — the 100ms-ish flush latency users feel between lines comes from the response writer's buffer, not from the encoder.
  - `Cache-Control: no-cache` + `X-Accel-Buffering: no` is the standard NDJSON header pair for streaming through nginx/Cloudflare proxies. Without `X-Accel-Buffering: no`, nginx will buffer the entire response before forwarding — defeating the streaming the SDK iterator depends on. Same trick used by Server-Sent Events endpoints.
  - When designing iterator-based SDK methods, return the generator from a non-generator function (here `execute_stream` is `def`, not just `yield from`). That way the HTTP request fires when the user calls `execute_stream(...)`, not when they pull the first item — which means HTTP errors raise eagerly at the call site, before the user's `for` loop. Lazy generators work but bury HTTP errors inside the iteration which is a worse UX.
  - `http.Flusher` is an OPTIONAL interface on `http.ResponseWriter`. Always do `flusher, _ := w.(http.Flusher)` and guard `if flusher != nil { flusher.Flush() }` — `httptest.ResponseRecorder` and some custom test writers don't implement it. The handler stays correct (no flushing means callers see all lines at end-of-response, which is fine for tests).
  - Python `httpx.Client.send(req, stream=True)` returns a Response whose `iter_lines()` consumes the body line-by-line. Pair it with a `try/finally` that calls `resp.close()` so the socket is returned to the pool — otherwise the test suite's connection cap can leak across runs. The urllib fallback iterates the response object directly (`for raw in r:` yields one line per iteration); both code paths share the same SDK-side `_consume_ndjson` so the iterator contract is identical regardless of transport.
  - `Accept: application/x-ndjson` on the request side is courtesy — the server doesn't content-negotiate (`?stream=1` is the actual switch) — but it makes the wire trace self-documenting and keeps the contract clear if a future server adds explicit content-type negotiation.

- **Learnings for future iterations:**
  - Cache key MUST canonicalise nested structures, not just top-level map keys. `json.Marshal` on a `map[string]interface{}` already sorts top-level keys alphabetically, but values that are themselves maps (or slices of maps) inherit Go's nondeterministic iteration order, so `{a:{x:1,y:2}}` can hash differently across runs. The recursive `canonicalJSON` walker fixes this; the `TestKey_NestedMapsCanonicalised` test would have failed otherwise. When reaching for `json.Marshal` as a "canonical" form, walk yourself unless you're sure every value is a scalar.
  - Pointer-typed Update DTO field (`Pure *bool`) is the right shape for ANY boolean toggle on an Update request. Bare `bool` collapses "omit ⇒ preserve" and "send false ⇒ clear" into one, silently disabling the feature whenever a partial update doesn't mention the field. `UpdateFunctionRequest.Runtime *string` and `UpdateLinkTypeRequest.IsRequired *bool` are prior art for this pattern; follow the same shape for any toggleable optional setting.

Reconstituting items from cache would need a `[]interface{}` projection layer plus per-item `flusher.Flush()` calls — strictly more complexity than US-221 calls for. The `narrow-interface-on-PGRepository` rule (US-202/US-203/US-210/US-214) only applies to NEW resource types with their own table.
  - When adding a new optional `OMSHandler.SetXxx` hook, follow the trio established by US-218: (1) define a narrow interface in `pkg/oms` (one or two methods only), (2) put the concrete implementation in a leaf subpackage with no `pkg/oms` import, (3) wire via setter on `OMSHandler`.   - Never `cp api/openapi.yaml cmd/server/openapi_spec.yaml` from memory — always run the explicit `cp` after the canonical edit. The contract-tests trio fails with a precise diff if you forget, but it's faster to make the sync part of the same `Edit` step in the tool transcript.

Splitting them lets contract tests fake one without faking the other, AND it documents the two consumer-distinct roles the *PGRepository plays in this adapter.   - `?asOf=<RFC3339>` over the wire is the canonical Foundry / Time-Travel idiom — RFC3339 (with Z suffix) is the only format `time.Parse(time.RFC3339, raw)` accepts, so consumers that send RFC3339Nano or "2026-01-01" (no time) get a clean 400 with `InvalidAsOf` rather than a silent zero-time fallback. ## 2026-04-18 - US-225 Random Sampling
- Added `sample` ObjectSet type (`Definition.Type="sample"`) with two new pointer fields: `Size *int` (required, >0) and `Seed *int64` (optional deterministic PRNG seed). Pointer shape lets an absent `Seed` stay distinguishable from zero — matches `NumNeighbors *int` prior art on the same struct.
- Validate: requires `ObjectSet`, `Size != nil`, `*Size > 0`. Zero / negative size errors explicitly (caught BOTH branches to keep the validator loud about intent).
- Execute: executes the inner set, then Algorithm R reservoir sampling over `inner.PrimaryKeys`. PRNG is `rand.New(rand.NewSource(seed))` when seed is set, else `rand.NewSource(time.Now().UnixNano())`. When `Size >= len(inner)` returns the inner slice unchanged (fresh copy; no shuffling required for "sample everything"). Empty inner returns empty without error. `Truncated` flag propagated from the inner — the sample is a strict subset of the inner's possibly-approximate universe, so approximate-in means approximate-out.
- Reservoir sampling (`reservoirSample`) is the right shape here because the inner set can be arbitrarily large (up to BaseExecutionCap = 10000) and we want the algorithm to stream through it once. Algorithm R is a well-understood 6-line implementation and produces a uniform k-sized sample with known statistical properties; no `ORDER BY random()` equivalent exists at the Bleve layer so this is the natural choice for Weave.
- OpenAPI: added `sample` to the `ObjectSetDefinition.type` enum, bumped the schema description, added `size: integer` + `seed: integer (int64)` properties. Synced the embedded `cmd/server/openapi_spec.yaml` so `TestContract_EmbeddedSpecMatchesCanonical` stays green.

  - ParseDefinition: JSON round-trip (type + objectSet + size + seed).
  - Execute: smaller-than-universe (asserts distinct + in-universe); larger-than-universe returns all 4 employees; seed determinism (same seed ⇒ identical ordered output); different seeds produce divergent output (size=3 from universe of 4 makes a collision statistically unlikely); empty inner returns empty; truncation propagation on the non-truncated path.
- All `go test -short ./pkg/... ./cmd/...` green; contract tests (AllRoutesDocumented + NoOrphanedSpecPaths + EmbeddedSpecMatchesCanonical) still pass; `go vet ./...` clean.
- Files changed:
  - `pkg/oss/objectset/definition.go` (Size + Seed pointer fields, Validate branch for "sample")
  - `pkg/oss/objectset/executor.go` (dispatch case "sample", executeSample, reservoirSample helper, math/rand + time imports)
  - `pkg/oss/objectset/sample_test.go` (new, 12 tests)
  - `api/openapi.yaml` + `cmd/server/openapi_spec.yaml` (sample enum + size + seed schema props, description update)
  - `prd.json` (US-225 passes=true)
- **Learnings for future iterations:**
  - Reservoir sampling (Algorithm R) is the idiomatic choice for single-pass streaming over an in-memory slice when you want a uniform k-sample. `ORDER BY random()` is a SQL pattern; we don't have a SQL execution layer for ObjectSets — the Bleve-returned PK slice IS the stream, so we sample in Go. A 6-line implementation is stable and matches what callers expect.
  - Pointer-typed fields (`Size *int`, `Seed *int64`) remain the canonical way to distinguish "not specified" from "zero value" on optional JSON-tagged struct fields. Three-state semantics apply here: Size=nil (required field missing, reject) vs Size=&0 (explicitly set to zero, reject) vs Size=&5 (accept). The validator's two-branch shape (`== nil` then `<= 0`) keeps the error messages specific to what the caller did wrong.
  - `math/rand` (not `crypto/rand`) is the right choice for reservoir sampling: we WANT a reproducible, seedable PRNG so the same seed produces the same output. `#nosec G404` is the annotation that tells a future linter pass "this is intentional, not a security-sensitive use". If a future story needs cryptographically unpredictable sampling (e.g. for audit-sampling where a caller can't predict what will be pulled) it would need a separate type or option — don't conflate the two.
  - When adding an ObjectSet type, remember the 3-step sync: (1) Definition.Type enum in `definition.go` + Validate branch, (2) dispatch in `executor.go::execute`, (3) `api/openapi.yaml` enum + schema props + embedded copy. Missing step 3 fails `TestContract_*` with a precise "missing entries" diagnostic — the contract tests are the canary.
  - Don't wrap the whole universe of sampled PKs behind a truncation toggle: `Truncated` reflects the INNER set's approximate-ness, not the sampling operation itself. A sample of a truncated universe is itself approximate (you might have missed PKs that WOULD have been sampled if the universe were complete), so forwarding the flag is correct. Reverse case also holds — sampling a non-truncated set is exact, so Truncated stays false.

  - Bleve's stored geopoint shape is `[]float64{lon, lat}` — NOT `[]interface{}`. `NewGeoPointFieldMapping()` accepts `[lon, lat]` arrays, `{lat, lon}` maps, or `"lat,lon"` strings on INDEX, but always stores as `[]float64{lon, lat}` and returns that shape via `hit.Fields`. Lon-first is the GeoJSON convention and Bleve inherits it. Any decoder MUST swap the order for idiomatic Go (lat, lng) returns.
  - When a PRD requests a specific library but that library violates a project invariant (e.g. cgo-free), pick the pure-Go alternative that satisfies the user-facing behaviour AND document the substitution in the story notes + progress log. The story title "Geohash / H3" lists both options; geohash is the natural first-choice implementation.
  - Geohash precision 1-12 is the natural character-geohash bound (each character is 5 bits of interleaved lat/lng). The PRD's "precision 1-15" wording was written with H3 resolution in mind; clamping to [1, 12] is the correct domain for character-geohash and matches mmcloughlin's library limit. Document the bounds as constants (`MinGeohashPrecision`, `MaxGeohashPrecision`, `DefaultGeohashPrecision`) so downstream SDK/docs consumers have one authoritative reference.

## 2026-04-18 - US-231 Cube / Rollup
- Added `Cube bool` + `Rollup bool` to `aggregation.AggregationRequest` and mirrored them on `objectset.AggregateObjectSetRequest`. Cube wins when both flags are set.
- `Engine.AggregateWithQuery` now branches to `aggregateCubeOrRollup` whenever either flag is set with a non-empty `GroupBy`. The path iterates the subset list returned by the new exported `ExpandGroupByCombinations(n, cube, rollup)` helper: cube yields every 2^N subset (full set first, grand total last, decreasing mask order); rollup yields the hierarchical chain `[gb[0..N-1]], [gb[0..N-2]], ..., [gb[0..0]], []` (N+1 entries).
- Non-grouped dimensions in a cube/rollup row are absent from `row.Group` — callers detect "aggregated" dimensions by key absence. The empty-subset grand total row has an empty `Group` map + request-scope metrics and participates in sub-aggregation wiring when the request also declared subAggregations.
- Cube + Having work together: Having is applied at the tail of `AggregateWithQuery` against the already-concatenated row list, so rows from any subset that fail the clause are dropped (e.g. filtering dept groups with count<2 drops HR from the dept-only subset while leaving the grand total visible).
- Derived-field aggregation parity: `aggregateWithDerived` now also expands via `aggregation.ExpandGroupByCombinations` when Cube/Rollup is set, feeding each subset through the existing `groupDerivedRows`. The exported helper lets pkg/oss/objectset reuse the engine's semantics without duplicating the combination logic.
- OpenAPI: new `cube` + `rollup` boolean properties on `AggregationRequest` and `AggregateObjectSetRequest` with descriptions explaining the Group-absence convention. `cmd/server/openapi_spec.yaml` synced (contract trio green).
- Tests (9 new cases in `pkg/oss/aggregation/cube_rollup_test.go`):
  - ExpandGroupByCombinations: 2-dim cube (4 subsets, full first + empty last + no duplicates), 3-dim cube (8 subsets), 3-dim rollup (4 subsets, hierarchical chain), cube-wins-over-rollup, neither-flag-set (single full subset).
  - End-to-end Aggregate: dept×active 2-dim cube emits 4+3+2+1=10 rows with consistent sum-of-counts per subset; dept×active 2-dim rollup emits 4+3+1=8 rows with no active-only subset; cube salary sum matches per-dept totals + grand total 465k; Having filter on cube drops below-threshold rows post-expansion; cube without any groupBy degrades cleanly to a single grand-total row.

- Files changed:
  - `pkg/oss/aggregation/engine.go` (Cube/Rollup fields, AggregateWithQuery dispatch, aggregateCubeOrRollup, exported `ExpandGroupByCombinations`)
  - `pkg/oss/aggregation/cube_rollup_test.go` (new, 9 cases)

- **Learnings for future iterations:**
  - Cube/Rollup are "meta-groupBys" — they expand ONE input into many grouping subsets. The right layer to hook them is BEFORE `recursiveGroupBy` (not inside it), so every subset reuses the existing grouping machinery with its own slice of GroupBySpecs. Putting the expansion outside the recursion keeps null-bucket handling, ordering, truncation propagation, and sub-aggregation attachment all correct without any duplicate code.
  - "Non-grouped dimension is absent from Group" is the right API contract for cube/rollup rows. Alternatives — embedding a marker string, or always including every key with nil — both collide with existing null-bucket semantics (a real null-group legitimately has `key=nil` in Group). Key absence is how SQL handles it (GROUPING() function), how Druid handles it, and how downstream clients are likely to expect it. Document this clearly in the OpenAPI description because consumers WILL hit this edge.
  - Cube on N dimensions returns 2^N groupings; at N=10 that's 1024 separate aggregations. This story did not add a hard cap (each subset shares the base query scope so the cost is moderate) but a future hardening iteration might reject `N > 8` or equivalent. For now, document the O(2^N) fan-out in the PRD/docs and trust callers to use discretion.
  - Exporting `ExpandGroupByCombinations` (public helper) instead of duplicating it in the derived-aggregation path keeps the two code paths strictly consistent. If a future story adds GROUPING SETS (explicit subset list) the expansion logic can grow to take an explicit subsets parameter AND keep the cube/rollup shortcuts — one helper, three entry points.
  - Cube with Having applies the filter to the CONCATENATED row list (all subsets merged), not per-subset. That's usually what users want — "show every grouping whose count >= 2" — but note the asymmetry: a grouping that's completely empty after Having simply vanishes from the response. The grand total row is unaffected unless its metric fails the clause too. If a future use case needs per-subset filtering, add a `havingBySubset map[int][]HavingClause` shape rather than overloading the top-level `Having`.

## 2026-04-18 - US-232 Fuzzy Search
- Added a new `fuzzy` WhereClause operator backed by `bleve.NewFuzzyQuery`. Unlike `MatchQuery.SetFuzziness` (which tokenises+analyses the input), FuzzyQuery treats the value as a single pre-analysed term and does one Levenshtein lookup against the index — the canonical primitive for "indexed token kafka, query kafca" cases called out in the PRD. The operator lowercases the input before handing it to FuzzyQuery so it matches the standard analyser's indexed form, rejects empty/non-string values, and falls back to `maxEdits=1` when no FuzzyConfig is supplied.
- Exported `where.MaxFuzziness = 2` as the single source of truth for the upper bound. `FuzzyConfig.MaxEdits` now documents "0, 1 or 2 (Levenshtein edit distance)".
- `POST /api/v2/ontologies/{ontology}/objects/{objectType}/search?fuzziness=N`: the handler now parses the query param, validates `0 <= N <= 2`, and REPLACES `body.Fuzzy` when the param is present. Explicit `fuzziness=0` disables fuzzy even if the body carries `fuzzy.maxEdits=1`. Invalid input (non-integer, out of range) returns a typed 400 `InvalidFuzziness` with the offending value in the `parameters` map. `body.Fuzzy.maxEdits` is validated with the same bounds when no query param is supplied.
- OpenAPI updated: `fuzziness` query parameter (enum [0,1,2]) on the search endpoint, `fuzzy` property on `SearchObjectsRequest`, and the supported-type list in the where-clause description now includes `fuzzy`. Embedded spec re-synced.
- Tests:
  - `pkg/oss/where/converter_test.go`: 7 new cases for the `fuzzy` operator — default-edits fallback, exact-token match, maxEdits=1 and maxEdits=2 thresholds, empty/non-string rejection, plus a type assertion that the produced query is `*query.FuzzyQuery` (guards against silent regression to MatchQuery).
  - `pkg/oss/handlers_fuzzy_test.go` (new): 6 handler-level cases — fuzziness=1 round-trip through Bleve, fuzziness=0 disables fuzzy even when body asks for it, fuzziness=2 with the `fuzzy` operator, out-of-range / non-integer values return `InvalidFuzziness`, body-level `fuzzy.maxEdits` bounds checking, query-string override wins over body.
- Files changed:
  - `pkg/oss/where/types.go` (export `MaxFuzziness`, doc update)
  - `pkg/oss/where/converter.go` (new `fuzzy` dispatch case + `convertFuzzy`)
  - `pkg/oss/where/converter_test.go` (+7 cases)
  - `pkg/oss/handlers.go` (parse `?fuzziness=` + validate bounds, override body)
  - `pkg/oss/handlers_fuzzy_test.go` (new)
  - `api/openapi.yaml` + `cmd/server/openapi_spec.yaml` (fuzziness param + fuzzy body field)
  - `prd.json` (US-232 passes=true)
- **Learnings for future iterations:**
  - A non-nil `FuzzyConfig{MaxEdits: 0}` is the "please default me to 1" sentinel, NOT "zero-edit exact match". The way to disable fuzzy at the converter level is `opts == nil` (or `opts.Fuzzy == nil`); at the handler level it's `?fuzziness=0`, which rewrites `fuzzy` to `nil` before calling the service. The first iteration of the `fuzzy` operator test tried to assert "maxEdits=0 disables fuzzy" and failed — don't repeat.
  - `strings.ToLower` on the FuzzyQuery input is load-bearing. Bleve's default text analyser indexes tokens in lowercase, so a raw `"Kafka"` FuzzyQuery matches zero rows because the index only contains `"kafka"`. MatchQuery hides this because it analyses its input with the same analyser. When adding a Bleve primitive that bypasses analysis (TermQuery, FuzzyQuery, PrefixQuery, WildcardQuery), always pre-lowercase the input.
  - `http.Request.URL.Query().Get(k)` returns `""` for both "not present" and "present but empty", so the `raw != ""` guard is the only way to distinguish "no fuzziness param at all" from "fuzziness=" (empty). The latter is arguably invalid input; `fuzziness=` with empty value currently falls through to the body path, which is a mild edge — documented here in case a future test wants to lock down the semantic.
  - The PRD phrasing "接入 Bleve FuzzyQuery" was the signal that `MatchQuery.SetFuzziness` alone was insufficient for sign-off — the acceptance criterion wanted the `*query.FuzzyQuery` type specifically. Future PRD items that name a specific Bleve type should be taken literally; substituting a behaviourally-similar primitive passes round 1 of review but fails the "is FuzzyQuery in the query tree?" grep.

## 2026-04-18 - US-233 Phrase Search + Slop
- Added a new `phrase` WhereClause operator. Two value shapes:
  1. Structured object: `{"phrase": "quick fox", "slop": 2}`
  2. Lucene-style string: `"quick fox"~2` (single or double quotes, slop optional). A bare unquoted string is accepted as the phrase with slop=0 so callers can always use the operator symmetrically.
- `pkg/oss/where/phrase_slop.go` (new): `ParsePhraseSlopValue(raw json.RawMessage) → PhraseSlopValue` tries the structured form first, then falls back to `ParsePhraseSlopString(str)`. The string parser only treats a trailing `~<digits>` as slop, so phrases with embedded `~` characters survive (test: `"foo~bar"~1` → phrase `foo~bar`, slop 1).
- `pkg/oss/where/phrase_slop_query.go` (new): `PhraseSlopQuery` implements `query.Query` and returns a custom `phraseSlopSearcher`. The searcher delegates to a `ConjunctionSearcher` of per-term `TermSearcher`s (so every phrase term must be present), then filters each matched doc by walking term positions: a phrase is accepted iff there exists an ordered term→location assignment whose summed edit-distance gaps (relative to strict adjacency) is ≤ slop. This mirrors Lucene's slop semantics (swapping two adjacent terms costs 2 slop, one intervening word costs 1) and bleve's internal `findPhrasePaths` logic — bleve hardcodes slop=0 at every `NewPhraseSearcher` call site so we couldn't reuse the internal searcher.
- `options.IncludeTermVectors = true` is forced inside the Searcher builder so TermSearchers surface Locations regardless of what the request asked for — without this the position map is empty and slop filtering returns nothing.
- `convertPhraseSlop` in `pkg/oss/where/converter.go`:
  - Routed via the existing `ConvertToBleveQueryWithOpts` dispatch (new `case "phrase"`).
  - Lowercases terms before hand-off (same treatment as `fuzzy`, `startsWith`, `containsAllTermsInOrderPrefixLastTerm`) so mixed-case input doesn't silently miss the lowercased-by-default Bleve index.
  - Slop=0 + multi-term falls back to `bleve.NewMatchPhraseQuery` (optimised path, identical semantics) — the custom searcher is only engaged when slop > 0.
  - Single-term phrases collapse to a plain `TermSearcher` (no conjunction wrap).
  - Slop is clamped to `[0, MaxPhraseSlop=32]` at the converter layer; out-of-range values produce an immediate error that the handler surfaces as a 400 `SearchObjectsFailed`.
- OpenAPI: `SearchObjectsRequest.where` description extended to list `phrase` as a supported operator and document both the structured and Lucene-style value shapes, plus the [0, 32] slop bound. `cmd/server/openapi_spec.yaml` synced; contract trio (AllRoutesDocumented + NoOrphanedSpecPaths + EmbeddedSpecMatchesCanonical) passes.

- **Learnings for future iterations:**
  - Bleve (v2.5.7) hardcodes slop=0 at every `NewPhraseSearcher` / `NewMultiPhraseSearcher` call site — `findPhrasePaths` accepts a `remainingSlop` parameter internally but it's always `0` from the public API. Any phrase-with-slop feature requires a custom `query.Query` that builds a conjunction of `TermSearcher`s and post-filters by position map. Don't try to reuse `bleve.NewMatchPhraseQuery` with its `Fuzziness` knob — that's per-term Levenshtein, NOT Lucene-style position slop.
  - `options.IncludeTermVectors = true` MUST be set inside the custom `Searcher()` builder before constructing the TermSearchers, not after — downstream searchers capture the options at construction time, so setting it on a caller-supplied `options` struct won't propagate. The position map in `DocumentMatch.Locations` is only populated when term vectors are included.
  - `DocumentMatch.Complete(scratch []Location)` folds the transient `FieldTermLocations` slice into the `Locations` map. Call `Complete` BEFORE inspecting `Locations` in custom searchers — without it, the map is often empty (the locations live in the scratch slice until you ask for them).
  - Lucene slop semantics: swapping two adjacent terms costs 2 slop (each term moves one position relative to strict adjacency). A one-word gap costs 1 slop. The dist formula `|expected - actual|` with `expected = prevPos+1` handles both gap and reversal uniformly — no branching on direction.
  - Lucene-style syntax parser: only treat the LAST `~<digits>` as the slop delimiter (`strings.LastIndex + isSlopTail` that requires all-digit tail), so phrases legitimately containing `~` survive the round-trip. First iteration used `strings.Split("~")` which broke on "foo~bar"~1 — regression test added.

Matches the US-232 `q.(*query.FuzzyQuery)` assertion pattern.
  - New WhereClause operator checklist (3-step sync): (1) add the `case "xxx"` in `ConvertToBleveQueryWithOpts` dispatch, (2) write the `convertXxx` helper with typed value parsing + validation, (3) extend the operator list in the `SearchObjectsRequest.where` description in `api/openapi.yaml` AND sync `cmd/server/openapi_spec.yaml`.
