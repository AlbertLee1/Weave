## Codebase Patterns
- ObjectSet snapshot subsystem has TWO distinct surfaces: (1) the in-memory `pkg/oss/objectset.Store` keyed by `createTemporary` RIDs (1h TTL), and (2) the durable `object_set_snapshots` table written via the `PersistedSnapshotStore` interface (US-224). The PG row interface lives in `pkg/oms` (`ObjectSetSnapshot` + `ObjectSetSnapshotStore`); the direction-of-dependency rule keeps `pkg/oms` from importing `pkg/oss/objectset`, so `cmd/server/object_set_snapshot_adapter.go` bridges them.
- A third durable surface — `saved_object_sets` (migration 000013) — is fully implemented (`pkg/oss/objectset/PGSavedStore`) but NOT YET wired into `cmd/server`. It has unit + integration tests but no HTTP route. New work that needs durable saved definitions can wire the existing store; no new schema is needed.
- Migration numbering convention: zero-padded `000NNN_description.{up,down}.sql`. Migrations are run with `golang-migrate`. As of US-365 the tip is migration 000082.
- Test build tags: unit tests run by default; `//go:build integration` tests need `go test -tags integration` and use `internal/testutil.StartPGContainer(t)` to boot a real Postgres container. The `ListEntries` helper on the in-memory `Store` is the canonical way to introspect ephemeral entries from tests.
- For canonical-JSON hashing across the codebase, prefer the `objectset.HashDefinition` helper (sorts keys, sha256 hex). Calling `json.Marshal` first is fine — the helper canonicalises again.

## 2026-05-02 - US-365 - ObjectSet 不可变快照持久化

**Implementation:**
- New migration `000082_saved_object_set_snapshots.{up,down}.sql` adds three columns (`definition_hash`, `snapshot_at`, `is_immutable`) to BOTH `saved_object_sets` and `object_set_snapshots`, plus the materialised PK columns (`frozen_object_type`, `frozen_primary_keys`, `frozen_truncated`) on `saved_object_sets`. A shared sequence `saved_object_sets_snapshot_seq` allocates monotonic snapshot transaction ids.
- `pkg/oss/objectset/persistence.go`: extended `SavedObjectSet` struct with the US-365 fields. `PGSavedStore.Create`/`Update` compute `definition_hash` (canonical-JSON sha256 via new `HashDefinition` helper) and pull `snapshot_at` from `nextval()`. New `ReapExpired(ctx, ttl)` method drops `is_immutable=false` rows older than ttl; new `RunReaperLoop` is a context-aware ticker driver suitable for cmd/server bootstrap. `Get`/`GetByName`/`List` round-trip the new fields with `COALESCE` defaults so legacy rows pre-migration read cleanly.
- `pkg/oss/objectset/store.go`: in-memory `storeEntry` now carries `snapshotAt` (allocated from a process-wide atomic counter `NextSnapshotAt()`). Exposed via `EntrySnapshot.SnapshotAt` so callers can prove `createTemporary` records a snapshot transaction.
- `pkg/oss/objectset/snapshot_persisted.go`: `PersistedSnapshot` and the wire response shapes (`CreateSnapshotResponse`, `GetSnapshotResponse`) now propagate `definitionHash`, `snapshotAt`, `isImmutable`. The `CreateSnapshot` handler stamps the hash via `HashDefinition(json.Marshal(def))` and allocates `snapshotAt = NextSnapshotAt()`; snapshots are always `IsImmutable=true` since they exist precisely to deliver byte-for-byte re-loads.
- `pkg/oms/object_set_snapshot.go` + `pkg/oms/pg_repository_object_set_snapshot.go`: extended `ObjectSetSnapshot` struct and the PG INSERT/SELECT to round-trip the new columns.
- `cmd/server/object_set_snapshot_adapter.go`: pass-through of the three new fields between `objectset.PersistedSnapshot` and `oms.ObjectSetSnapshot`.

**Learnings for future iterations:**
- The acceptance criterion says "saved_object_sets 表新增 ... is_immutable BOOL", but the durable mechanism currently delivering byte-for-byte re-loads is `object_set_snapshots` (US-224). I added the columns to BOTH tables so future stories that wire `PGSavedStore` end up consistent with the existing snapshot path. The `cmd/server` adapter (`object_set_snapshot_adapter.go`) is the right place to add new field passthroughs whenever an OMS row gains columns.
- The PG `Update` path on `PGSavedStore` allocates a fresh `snapshot_at` on every update — this is intentional: each save is its own "transaction". Tests cover this.
- For tests that need to backdate `created_at` to exercise the reaper, expose the `pgxpool.Pool` from the integration setup helper (see `setupSavedStoreWithPool`). Don't add a public accessor on `PGSavedStore` itself.
- `gofmt` rewrites the column-aligned struct field comments — keep them as plain bullet points or expect a fmt round.
- The acceptance criterion mentions a `/saveObjectSet` endpoint that does not exist in the codebase. The `CreateSnapshot` POST route (US-224) IS the durable-save path; satisfying the byte-for-byte invariant relies on its frozen-PK persistence. Future work may add `/saveObjectSet` proper — the `PGSavedStore` is ready.
- The TTL scheduler is delivered as `PGSavedStore.RunReaperLoop` rather than wired directly into `cmd/server/main.go`. Wiring is one Go statement once `PGSavedStore` is constructed: `go store.RunReaperLoop(rootCtx, time.Minute, time.Hour, nil, log.Println)`.
